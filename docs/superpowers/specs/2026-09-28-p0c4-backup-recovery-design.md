# P0-C4 完整备份与干净实例恢复详细设计

**状态：** 本文细化已批准的 [P0-C 总设计](../../../../../docs/superpowers/specs/2026-09-23-p0c-assets-jobs-portability-design.md) C4 节及[服务器部署与数据恢复设计](../../../../../docs/服务器部署与数据恢复设计.md)第 7–8 节。基线为 C3 提交 `4507f3f55f860a6d3afed2cefe2bce27f7ff6b7c`，状态 `P0_C3_VERIFIED / NOT_PRODUCTION`。本设计不代表 C4 已验收或允许部署生产。

## 目标与边界

把**一个整库一致恢复点**的 PostgreSQL 数据、全部权威原件字节、资产清单、模式/角色重建信息和非敏感恢复说明送到独立故障域；在全新隔离实例中完整恢复、核验后才允许标为可用。C3 的 `exact_import_v1` 只含选中阅读视图的授权闭包，不含用户、空间、grant、发布、请求收据和作业；其文件/大小预算也不是整库预算，不能作为 C4 备份。

本阶段恢复 P0-A/B/C 已存在的权威内容和记录；P1-B 学习事实出现后追加该闭包与回归。P1 登录、HTTP、前端、生产发布、自动定时和无停写连续归档不在 C4。备份文件、恢复目标及独立副本全部保持私有；密钥和密码不写入包、manifest、日志或测试证据。

## 方案选择

考虑过直接打包文件卷、重用 C3 包、整库 `pg_dump` 加完整原件清单。文件卷复制不能证明数据库一致性，C3 包缺整库状态。首版选择第三种：受控短维护窗内完成一致数据库 dump 和完整资产清单，再保护清单内不可变资产、释放写入、流式复制并验证独立副本。对已关闭所有业务客户端的隔离验收，允许以拒绝运行时连接实现维护窗；未来 P1 在线部署如要求阅读不中断，应接入明确的写闸与事务排空协议，不把客户端提示当成数据库级写阻断。

## 备份协议

1. 由独立的管理入口取得**管理角色**连接；业务 Worker 和 `learning_runtime` 无权发起备份、切换维护状态或读取整库。运行前固定源实例、数据库、资产根、备份暂存根、独立目标与工具版本。所有外部命令以参数数组调用，不经 shell 拼接；凭据来自独立私有文件或环境，输出必须脱敏。
2. 启用持久可核对的写闸，禁止新业务写入并等待在途业务事务收束；验收需证明所有现有写入口都被闸住，且闸失效或无法确认时不得继续。隔离验收先停止所有 runtime/Worker 进程，再由管理角色拒绝新 `learning_runtime` 连接，核对并排空既有会话和事务；发现其他业务写角色或无法证明排空就失败关闭。此时阅读也暂停，不能冒称未来在线只停写协议。禁止维护期间并发清理、源资产替换和新的业务写事务。`pg_dump` 和全量 `asset` 读取处于同一静止状态；若将来放开并发，必须改为同一导出快照协议。
3. 从 `asset` **全部 ready 行**采集 `(space_id,id,sha256,byte_size,storage_key)`，按 digest 去重得到实际字节集合；同 digest 元数据冲突、非规范 key、负数/溢出和缺失字节均失败。不能从 C3 选中阅读范围、当前可见头或资源引用推断全量范围。数据库 FK 与额外闭包校验共同验证引用；未被当前视图选中的旧版本、个人记录、授权、收据和作业仍在 DB dump 中。首版单次清单上限为 **100,000 个逻辑资产行、64 MiB 规范 `asset-index.json`**；超过时显式失败，不截断、不标 `complete`。目录采集只读取至上限加一行，以限制内存；这与 C3 的选择范围/原件预算无关。
4. 生成 PostgreSQL custom-format dump，校验命令退出码、非空文件与大小/摘要，并将模式迁移版本、PostgreSQL 主版本、应用提交、非敏感角色重建配方及其摘要写入版本化 manifest。备份控制状态保存在业务数据库之外，不能依赖尚未恢复的源库来判断包是否完整。
5. 为清单资产建立持久保留保护。只有 dump、清单和保护均已持久化，才解除写闸。保护在复制完成或明确废弃之前不得消失；异常退出按保守方式继续保护。生产端清理和备份端去重/保留分别计数，任何仍被有效备份引用的字节不得删除。
6. 把 dump、角色配方、manifest 和所有原件复制到独立故障域。每个资产使用既有 no-follow、安全目录句柄和流式 SHA-256 检查；目标端重新读取并校验大小/摘要。每份备份都带**完整清单**，即使字节物理去重。复制中断只留下不可用的 staging，不能覆盖上次 `complete`。只有源端一致性/保留保护证据和目标端全量核对都通过，管理进程才原子发布完成收据。完成收据不是可跳过重新校验的文本开关。具体异机传输方式是部署参数，单机第二目录不能自称独立故障域。

## 包与状态

首版普通私有目录包，不接受 ZIP/TAR 作为恢复输入。manifest 用固定 `backup_full_v1` capability、格式版本、备份 ID、源应用提交与构建 SHA/PG/迁移信息、逻辑资产数与去重字节数、按规范路径排序的 `FileRecord {path,size,sha256}`；文件包括固定数据库 dump、角色配方、按 `(space_id,id)` 排序的 `asset-index.json` 与每个 `assets/sha256/<前两位>/<digest>`。资产索引逐条保存所有 `(space_id,id,sha256,byte_size,storage_key)`，不是仅存数量；恢复后与 DB `asset` 行逐行比对。迁移身份保存按版本排序的完整 `(version,checksum_hex)` 集合及其规范 SHA-256 指纹，不能只记最高版本。本轮隔离验收的兼容规则固定为 `backup_full_v1`、PostgreSQL 主版本 18、源/目标 `_sqlx_migrations` 的版本与 checksum 完整集合一致、恢复二进制与来源应用构建 SHA 一致；未知或不匹配明确拒绝，跨构建升级恢复以后另验，不能以降级试错。Task 1 记录这些字段与基础格式拒绝，环境比对在 Task 4 做。控制状态分 `staging`、`sealed`、`complete`；其中只有经源端一致性证据及独立目标全量校验的 `complete` 能作为恢复输入。manifest 的规范字节和完成收据都带 SHA-256，未知版本、额外/缺失文件、链接/重解析点、路径碰撞、非规范 digest 或大小不符一律拒绝。SHA 只检测无意损坏和未重新计算的篡改，不能证明对有包写权限攻击者的真实性；信任边界是仅管理进程可写的私有 0700 目标及独立运行证据。恢复入口在**任何目标数据库写入之前**仍重新验证整个包。空资产集合合法，但 dump、角色配方和空资产索引仍是必需。

## 干净恢复

仅接受新建、未对用户开放的数据库和资产根。先核对完成收据、manifest、全部文件和适用的 PostgreSQL/应用版本；角色由单独受保护的凭据和已核对的非敏感配方建立，不从包恢复密码。导入 custom dump 与原件，校验所有 `asset` 行与文件集合一致及关键业务引用；**全部**源实例运行中租约令牌在目标上失效，不仅是墙钟上已过期的租约。可重试作业按原次数/上限重新排队，已产生外部副作用的作业先按幂等记录核对，不盲目重发。重建派生预览/索引；重建失败时可保留内部只读恢复态，但不将实例标为可用。核对固定旧版/当前版、个人 gap/unplaced、关系/审查、位置和权限后，独立的验收标记才能放行访问。

恢复缺文件、错误摘要、坏角色、脏目标、版本不兼容、SQL 恢复非零退出、租约/引用闭包异常均失败并保持隔离；不得用部分恢复结果替换唯一可用实例。备份复制中断、恢复缺文件、摘要篡改、同 SHA 冲突、异常退出后写闸/保护恢复和四套旧版升级为必测失败/回归。

## 安全与验收

管理备份进程与业务 Worker/导出进程分开，最小权限及私有 0700 目录；日志只记录阶段、匿名 ID、退出码、摘要和计数，不记录原文、密码或完整 DSN。每个 Linux 验收批次使用新 Compose 项目、新数据库/卷和明确未占用子网；服务器源码包、摘要、目标路径逐包由用户单独授权。保存失败批次、清理结果、源码/产物哈希和原始脱敏证据。C4 通过门是干净实例全链恢复及负面注入、格式、严格 Clippy、工作区回归、四套冻结旧程序升级均实测成功；此前不称生产完成。
