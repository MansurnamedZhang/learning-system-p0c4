# P0-B3 关系与认识审查设计

2026-09-21 · P0_B3_VERIFIED / NOT_PRODUCTION · 逐任务子代理实施与独立审查完成；宿主与全新 Compose 各 222 项通过，B4 尚未实施

前置基线：P0-A、B1、B2 已验收；B2 宿主与空库 Compose 各 105/105。本文细化已批准的 P0-B 路线，不改变 PostgreSQL 为权威库、首版不常驻 Neo4j 的决定。

## 1. 本阶段交付

让“猜想—证据—反例—结论”成为可保存、可复现、可撤回、受当前权限约束的数据链。正文修订、关系修订和人工审查分别留史，互不覆盖。

本阶段仍是 Rust 核心库与 PostgreSQL 存储接口。网页、HTTP、登录、图片原件管理及全图影响遍历不在本阶段。B4 再负责反向查询和知识修订影响范围。

采用架构设计路径：本次涉及内容契约、授权闭包、关系身份和多个事务边界；先确定这些规则，再写施工单与实现。

## 2. 方案选择

| 方案 | 收益 | 代价与结论 |
|---|---|---|
| 关系和审查写入块正文 | 初期表少 | 改审查必须改正文，历史证据与当前判断混在一起，不采用 |
| 独立关系、独立审查、固定引用 | 版本边界明确，复用现有事务与授权能力 | 需要统一读取投影，推荐 |
| 同时引入 Neo4j 双存储 | 可增加图查询实现 | 多出同步、撤权和重建一致性工作，尚无必要，本阶段不采用 |

## 3. 四种事实分开存储

| 对象 | 保存内容 | 更新方式 |
|---|---|---|
| BlockRevision | 正文、用途、严格内容依赖 | 新增正文修订 |
| RelationRevision | 精确端点、关系类型、理由、条件、范围 | 新增关系修订 |
| RelationReview | 对某一个关系修订的人工复核或撤回 | 追加审查记录 |
| EpistemicReview | 对某一猜想/结论修订及固定依据的条件化判断 | 追加审查记录 |

固定引用分为 BlockRef、RelationRef、RelationReviewRef、EpistemicReviewRef，均包含所属稳定身份及确切修订/记录身份。不同引用类型不能互换；不接受 latest、仅块 ID 或客户端自填作者。

### 关系身份与去重

关系稳定身份固定“范围、类型、两端块身份”；关系修订可更新两端所指正文版本、理由和条件。改变类型、范围或两端块身份，创建新关系。接纳旧关系到 H@2 必须显式新增关系修订，不能后台自动漂移。

范围使用严格枚举 Space 或 PersonalOverlay。个人层范围必须属于指定空间且当前 actor 有该层管理权；范围不赋予端点读取权。

用户类型沿用 annotates、questions、answers、inspired_by、supports、opposes、tests、related_to。有向关系只保存一个方向。related_to 按稳定块身份排序，完整端点随之交换；数据库唯一键约束同范围、同类型、同端点身份只有一个关系身份，并在并发创建时生效。不同理由与条件通过关系修订表达，不创建平行重复关系。

本阶段普通关系拒绝同一块身份连接自身；正文跨版本演进由修订链或系统谱系表达。不同块间语义关系允许环。

### 两类审查

RelationReview 状态为 unreviewed、reviewed、needs_recheck、withdrawn。缺少理由或适用条件的 supports/opposes 可先保存为 unreviewed；标记 reviewed 时必须提供说明，不能以“已复核”代替对命题的判断。

EpistemicReview 状态沿用 untested、testing、inconclusive、supported_within_scope、refuted_within_scope、superseded。target 必须是指定修订的 conjecture 或 conclusion。记录固定关系修订、所选关系审查、证据修订、条件、判断理由和前序审查引用。

supported_within_scope / refuted_within_scope 必须有明确条件、理由和相应方向的依据；这是结构完整性要求，不是机器证明。审查不能把指向 H@1 的证据关系当作 H@2 的依据。其他状态允许“暂无线索”的空依据记录。

同一审查流串行追加，使用 expected_previous 防止并发静默覆盖。reviewer 与时间由服务端生成。结论 C 是普通 conclusion 块，其 basis_refs 可固定引用 H、证据及人工审查；不复制出第二份关系事实。

## 4. 内容 v2 与兼容

保留现有 TextDraft、content-v1 规范化字节和摘要算法。v1 仍拒绝 basis_refs、target 等未知字段，不通过增加 optional 字段扩展旧契约。

新增显式内容版本分派，v2 使用独立规范化域与严格类型。覆盖三种形态：带结构化依据的文本、固定 target 的引用卡、保存固定关系修订列表的 relation_view。basis_refs、target、requires_context 全部进入同事务引用索引；禁止只存 JSON 而不登记依赖。

旧 API 保留 v1 适配入口；组合、发布、个人阅读等内部读取切到统一版本模型，不得把 v2 当成 v1 强制反序列化。旧数据库行、摘要和已发布清单不改写，未知版本明确拒绝。

requires_context 是正文完整性依赖；basis_refs 是依据；target 是引用卡目标。三者保留不同角色，不自动生成 supports，也不靠解析 Markdown 链接形成权限依赖。

动态关系查询定义属于工作态。B3 保存固定 relation_view 列表；B4 再增加动态查询能力。引用卡内嵌最多两层，遇环转为回跳链接；授权和发布闭包仍需检查完整依赖，不能在两层处停止安全校验。

## 5. 当前授权优先于历史快照

统一授权投影供正文读取、批量回读、阅读融合、关系、审查和发布使用。禁止暴露可绕过该投影的按 ID 正文回读接口。

| 情况 | 对外结果 |
|---|---|
| 请求对象自身不可读或不存在 | 相同的不可用结果 |
| 可读 v2 块有不可读的结构化必要依赖 | 整个正文投影不可用；不返回部分原始 JSON、隐藏 ID、标题或引用数量 |
| 关系自身或任一端点/必要依赖不可读 | 整条关系不进入可见结果 |
| 可读审查的依据不再完整可读 | 仅返回通用“当前无法完整核对”状态，不输出判断正文、依据标识或缺失数量 |
| 列表中有不可见项 | 过滤后分页与计数，不输出原始序号、过滤数量或隐藏占位 |

所有正文、理由和条件按所属记录一起授权，不尝试自动删改自由文本中的秘密。系统无法识别用户手工写在文字中的敏感内容；结构化依赖必须显式登记。不可用投影不携带原始内容摘要，避免成为隐藏内容的比较通道。

旧快照固定“当时选择了什么”，不固定“现在仍有权读取什么”。恢复权限后可再读同一个历史快照，不生成伪造的新版本。已保存历史判断与“当前完整可核对”分开显示；后续撤回不改写旧审查，但当前审查记录不会自动冒充历史选择。

B3 闭包设置服务端节点、边、深度和字节预算；超限明确报错，保存/发布不能把截断当完整。具体常量在施工单中结合 B1/B2 现有预算统一确定。

## 6. 阅读与发布衔接

新增版本化阅读快照契约，固定关系修订及所选审查记录；旧 B2 快照语义保持原样，等价于未选择关系。变更关系选择创建新视图修订，不必改正文或个人层内容。

编辑、迁移和只读投影都必须识别新快照版本。迁移保留既有精确关系选择，不将 H@1 关系重定向到 H@2；不适配当前原文的选择可显示为历史关联，前提是其端点及上下文可读。

新发布版本收集正文依赖、固定关系和审查的完整闭包，全部验证后原子保存。历史 B1 发布清单原样保留；不能为了 v2 把旧发布重算为新摘要。

## 7. 派生、拆分、合并

提供独立内容操作，创建输出块、初始修订、操作记录和系统谱系，并在一个事务内提交。普通关系接口不能写 derived_from、split_from、merged_from。

- 派生：一个输入精确修订，生成一个新稳定块身份。
- 拆分：一个输入精确修订，生成至少两个不同的新稳定块身份。
- 合并：至少两个不同输入块的精确修订，生成一个新稳定块身份。

输入必须当前可读，输出空间可写。原块与原组合不变；把输出替换进文档或迁移个人层需调用对应显式操作。谱系只说明来源，不证明输出与输入语义等价。

## 8. 写入与并发边界

沿用 actor/request_id 全局幂等命名空间，载荷不同的同键请求拒绝。重放仍检查当前权限；不因命中旧回执泄露已经隐藏的引用。

写入统一锁顺序：请求锁 → 排序后的空间授权锁 → 各操作固定顺序的身份/头锁。新增依赖涉及的全部空间先解析再锁定并复验，防止检查后撤权竞态。关系端点使用复合外键，修订与索引同事务写入，审查仅追加。

施工单需给出各命令锁表、唯一键、迁移约束、失败回滚点和错误合同；不能只依赖应用层“先查询再创建”实现对称去重。

## 9. 真实场景与验收

使用明确标注为合成业务数据的 Attention 样例，不声称完成科学实验：H@1 提出限定条件下的猜想，E1/E2 为同一来源运行的观察，X 为反例。人工保存 supports/opposes 关系、条件化审查，再形成 C@1。

| 验收 | 必须证明 |
|---|---|
| H@1 → H@2 | 旧关系、旧判断和 C@1 不自动跟随新版 |
| 修改关系或撤回 | 端点正文摘要不变，旧快照仍可复现其固定选择 |
| E1/E2 同源 | 仅按显式来源运行分组，不推断独立性或按数量确定真假 |
| E1 撤权 | basis_refs、target、回读正文、审查、关系、列表计数都无隐藏标识或内容泄漏 |
| 并发 | related_to 正反创建不重复；过期头、重复请求和撤权竞争结果确定 |
| 内容升级 | v1 黄金摘要不变，旧数据升级可读，v2 缺依赖或未知版本拒绝 |
| 读取一致性 | 单项、批量、融合、历史快照和发布读取使用同一授权语义 |
| 谱系 | 拆分有多个新稳定 ID，原版可读；事务故障不留下半套输出 |
| 闭包与环 | 内嵌展示有界，必要依赖验证不能被展示上限绕过，超预算不假称完整 |

来源运行使用固定来源块引用，不接受未经校验的任意字符串冒充独立运行。自动生成实验运行、统计检验与 AI 审查不在本阶段。

历史数据库实验的两类权限缺陷必须在实际 Rust/PostgreSQL 接口上分别建立回归。保留原实验 NOT_PASSED 历史记录；通过新实现测试也不能改写原实验结论。

## 10. 实施前的交付顺序

设计确认后编写分关施工单：

1. 内容版本分派、严格引用及统一授权投影。
2. 关系身份/修订、并发去重与关系审查。
3. 认识审查、固定依据及同源分组。
4. 固定阅读与发布契约升级。
5. 系统谱系和端到端验收。

每关先定义失败用例，再实现与验证；最终在本地 Linux 隔离环境完成旧库升级、全量回归、空库 Compose 和审查。当前已获实施授权，按施工单推进，验收结果单独记录。

已确认的新增设计取舍：同端点同范围只保留一个关系身份；隐藏必要依赖时整体正文不可用；B3 同时覆盖派生/拆分/合并。这些规则作为施工依据。
