# P0-C4 Remaining Completion Design

2026-10-04; adopted 2026-10-05. This document refines the approved [parent backup/recovery design](2026-09-28-p0c4-backup-recovery-design.md) and remaining parent Tasks 3/4/5. The [implementation plan](../plans/2026-10-04-p0c4-completion.md) tracks implementation and actual acceptance. The user authorizes code and single-host full-chain work now; no independent destination is currently available. All implementation tasks and new acceptance results remain pending at adoption.

The nine-task decomposition and initial operational caps are adopted. Appendix A fixes the registry format/interfaces and Appendix B preserves recovery with the source unavailable. Existing controlled-import fixture: one probe table with two rows; historical execution does not prove new code.

## Outcome and invariant

Recover every authoritative P0-A/B/C database row, its schema/permission behavior, and every ready original asset byte into a newly born isolated PG18 instance. Backup storage, management state and credentials remain outside business databases. Only final verified recovery can be usable; missing originals, unknown effects, interrupted commits or identity uncertainty stay isolated.

Single-host work produces an explicitly quarantined full-chain rehearsal from a fresh source capture, without manufacturing CompleteBackup. The normal public restore path still consumes independently witnessed CompleteBackup. No shared `allow_local`, `skip_complete`, caller-supplied expected pin, generic SQL input, or caller HashSet may become recovery/cleanup authority.

Preserve all migration bytes, source journal v1 bytes, C1–C3 APIs, original source/build/control binding and old-attempt semantics. Old attempts continue to require their original audited lifecycle-capable binaries and original roots; the latest binary cannot adopt them merely because their bytes or build profile match. Preserve historical evidence and all old resources.

## Decisions and alternatives

| Choice | Viable approaches | Recommendation |
|---|---|---|
| Durable storage identity/protection | Extend business DB; compile every asset/pin root into a new binary; independently provisioned management registry plus per-attempt sidecars | Registry. It survives missing source DB, supports restart/discovery and avoids a new caller pin or business migration. Keep existing control build pin intact rather than replacing it. |
| Full DB import | Direct pg_restore connection after preflight; rerun migrations then parse data-only dump; reuse explicit writer protocol with same-build fixed schema/ACL contract and bounded COPY frames | Third. Direct invocation loses writer-side lock/commit barriers. Migration-first loading activates insert triggers that reject historical job/receipt states and alters migration execution evidence. A complete schema dump naturally loads data before post-data triggers/FKs, and exact schema admission preserves the existing restricted trust boundary. |
| Single-host work | Block all work until destination exists; fake off-host key; private test-only full-chain adapter consuming a fresh SourceLocalPin | Private adapter. It shares the real restore engine but cannot return CompleteBackup or usable authority, and always quarantines the target. Test signing keys remain signature-unit-test inputs only. |
| Retention | Add automatic GC; keep every enrolled protection reference and expose read-only reference counts/discovery | Keep/protect. This stage needs crash-safe retention, not deletion. Abandoned artifacts remain protected. Explicit retirement/deletion can be a separately reviewed later feature. |

## 1. Independently provisioned management registry

Add small Rust modules `registry.rs` and `protection.rs` in learning-backup, plus a focused root-only Python provisioning adapter `scripts/p0c4_storage_registry.py`. The ordinary backup APIs consume registry authority; they do not initialize it, enroll arbitrary caller paths or supply expected hashes. Installation/isolated provisioning is separate from operation startup.

In the trusted management namespace, use fixed `/var/lib/knowweave-c4/registry` with root-owned non-writable ancestors, 0700 directory and 0600 ordinary single-link records; no environment/path override in production API. The privileged provisioner is within the existing trusted root/Docker boundary. It creates the canonical deployment record, existing lock and append-only enrollment records before operational binaries start. A test-only namespace adapter is private to unit tests; real acceptance mounts the fresh registry volume at the fixed path. No compile-time registry fingerprint supplied by the operation caller.

Each enrollment binds random deployment/group/enrollment UUIDs, root kind, canonical path, held dev/inode and expected uid/mode. Source-group records additionally bind DB/control/build identity. Immutable authority.json binds the registry's own original dev/inode and lock/metadata subdirectory identities; copying the entire registry bytes into a substitute directory fails. Append-only generation commit files identify the complete sorted root/group roster. No markers are added to source control, local-pin, sealed-package, asset or staging trees. Enrollment identity lives only in the separate registry. A valid complete rollback by privileged management is outside the existing trusted-root threat model; ordinary stale records/snapshots fail generation and full-roster consistency checks.

Acquire existing source DB admission first, then registry `flock(LOCK_EX | LOCK_NB)`, then relevant-group roots in enrollment-ID order. Busy returns fixed `BackupError::Invalid("registry busy")` immediately; never synchronously wait inside Tokio. Discovery needing DB references follows the same source-admission-first order. Destination-only reopening never requests source admission. Keep registry lock and held handles through source phase publication/release; recheck immutable snapshots before release/publication. Lock substitution, bounded scan failure or incomplete authority returns a blocked result, never an empty protection set.

Registry caps: at most 1,024 enrolled roots, 256 groups, 128 generation commit files, each enrollment/group <=16 KiB, generation roster <=512 KiB; at most 100,000 discovered attempt/protection filesystem entries; 512 MiB aggregate metadata/protection scan reads per operation and at most 100,000 unique protected digest keys across the requested source group. The key limit includes the DB/backup union. Per asset index remains 100,000 logical rows/64 MiB. Count cap+1 while enumerating, charge reads before allocation, and include repeated verification reads in the same operation budget. Overflow blocks all reporting/release/publication; never return partial candidates. Full asset/dump byte hashing has its own streaming/manifest limits and is not mislabeled as metadata scanning.

New manager code requires independently provisioned registry before any journal/ACL/dump mutation, including close-only, finish and abandon. Archived original manager plus original binding retains its original behavior for old attempts; current managers have no legacy bypass/auto-enrollment. Current focused fixtures are independently reprovisioned and rebuilt with a fresh registry; archived fixture binaries/records are neither changed nor reused as current acceptance.

## 2. Attempt protection and reconciliation

Before a new source journal/ACL mutation, establish a durable `capture_pending` protection sidecar in the registry linked to attempt/source/control/assets/staging/pin identities. This blocks all candidate reporting for those storage roots until the asset catalog is known. After drain/catalog collection, write canonical full asset-index-derived protection keys and its manifest binding. After sealed-pin verification, record immutable pin identity, index/manifest SHA and `retained` protection. Preserve both records with monotonic linkage; any partial state remains conservatively blocking.

Integrate prepare, finish and abandon. Finish must discover the original registered root set, all relevant records and actual pin bytes before any GRANT; abandonment may reopen only under its current safe lifecycle semantics and preserves every protection record (`keep_all`). Source journal v1 remains untouched; additive sidecars must not be placed inside directories whose exact-tree rules reject extra files. A new capture is not allowed to hide an unresolved attempt via fresh enrollment. Snapshot registry and every relevant source-group asset/staging/control/local-pin root, source journal, abandonment and protection record before release. Global roster integrity is checked, but destination-only recovery does not physically reopen unrelated historical/source roots. A terminal ambiguity remains manual.

`discover_backup_protection` returns an opaque `ProtectionSnapshot`, with privately held keys and root/generation identity, or an error. `reconcile_registered_assets` adds independently read DB asset/upload references under management admission and passes the union internally to existing dry-run reconciliation. It must withhold all candidates on unknown/corrupt/stale/unreadable registry or unfinished pre-index capture. Backups still protect a blob after its live DB reference disappears; shared blobs carry separate backup reference counts. Pin/package retention discovery is separate from source-store reconciliation; no backup directory is handed to `FsAssetStore::reconcile` for deletion. Neither API deletes bytes or authorizes later unlinking. Caller HashSet remains a low-level C1 API, not the management proof.

## 3. Source exact endpoint and capture ownership

Close the explicitly open source same-ID physical-clone gap. Add `source/endpoint.rs`, composing the already reviewed exact Docker ID/daemon/mount/postmaster checks and live SQL-session challenge helpers through narrow crate-private sharing. Source DB name/OID/system ID alone remains insufficient. A source permit owns admission and ephemeral random session challenge locks, the independently observed exact source-container identity and local Unix socket route. The child socket observer must see the admitted backend identity and both locks in that exact container before dump; an observer aimed at a physical clone fails before source journal/ACL/dump mutation. Recheck identity throughout capture and before release. Every check preserves original source root/build binding.

The dump child runs `/usr/lib/postgresql/18/bin/pg_dump` inside that exact PG18.6 container, with cleared environment, fixed socket/port/user/database argv, no caller host, no shell and no caller flags. Reuse the tested bounded process supervision; stream output into a private held descriptor, cap dump size and elapsed time, own child/pipe until wait/reap/quarantine. If the source postmaster changes, admission connection and challenges fail; output stays unusable and release is forbidden. Controlled source errors keep CONNECT closed. Keep legacy `PgDumpSpec` contract for old capable binaries, but new enrolled capture uses the bound adapter. A source cleanup failure must not be reported as confirmed stopped merely because the Docker CLI was killed.

The current management executor already runs through verified Docker exec inside the source PG container. Use its native fixed local-socket child for capture; it does not have a Docker socket and must not be moved to a weaker host route. Independently installed management observations bind the executor's actual namespace, exact source image/container/mount/postmaster facts and epoch. A narrowly fixed host broker may refresh those observations and child lifecycle facts using nonce/challenge fields; it does not accept commands, SQL, paths, host/port options or dump bytes. The source validator is separate from the restore-target birth validator, whose four-mount/health/prefix contract is unchanged. An executor outside the attested source namespace fails closed. This deployment constraint applies to the shipping source capability as well as the test adapter; test hooks alone are insufficient authority.

Internally, the verified source-isolation reader may return a private held proof carrier, and the endpoint/supervisor owns the original `SourceAdmission` rather than borrowing a session that cancellation could release early. Cleanup must retain the admitted session, relevant enrolled/root/protection authority and child ownership until reaping and quarantine complete. Public configuration and registry/source-journal-v1 schemas remain unchanged; no caller pin or bypass is introduced.

The source capability is delivered through the existing non-test library API and installed non-test observation producer; this task does not introduce a generic management service. Its deployment notes must identify the exact PG executor and executable prerequisites, and explain the old separate-manager route's refusal. The named restart-or-lock-loss live case may exercise actual random-lock loss; its evidence must explicitly distinguish this from an actual postmaster restart. Epoch/namespace drift unit tests and fixed case names cannot establish a real restart observation. Any later acceptance requiring a real restart must use a separately observed external lifecycle action.

The fixed native source-bound capture case retains its healthy original asset set and independently validates its exact keys, ordinary-file metadata, full hashes and sizes against the ready-row/index/sealed copies. The legacy retention capture case still explicitly removes only its three fresh synthetic originals and must prove their absence. Both require the complete sealed inventory, source/build/migration linkage and genuine bounded TOC validation. Select this fixture policy only from the fixed accepted test identity; do not add a caller bypass, skip the capture audit, transfer original-loss credit to native binding, or remove healthy source files to satisfy the wrong fixture expectation.

## 4. Destination completion

Reuse `transfer_sealed_backup`, `DestinationStatement` v2/P-256, existing trust config, `publish_complete_backup` and full reopen verification. Add a focused destination verifier management executable/adapter that opens the enrolled destination itself, rehashes every byte, verifies captured manifest and released/protected source statement, then signs canonical statement with the destination-owned private key. The source receives only public trust material and witness bytes; never include key/credentials in source archives, Git, manifest or evidence.

Publication additionally requires the held source registry/protection snapshot and registered destination roots, and rereads the previous complete package untouched after a failed new transfer. Existing v2 signature/manifest formats need not change; persist additive management evidence binding the protection snapshot. Recovery reopens destination trust and captured source evidence; it must not require the original source DB, source registry or source host to still exist. If a future format must change, reject unknown versions explicitly instead of silently accepting a weaker v2 record.

This deployment currently cannot pass the independent-domain prerequisite. Implement and negatively test the default-closed path now. Unit tests can check signature verification with fixture keys but must not enable an operational same-host CompleteBackup path. A real destination rollout later requires a separately operated host/storage domain, independent private-key custody, identity review and fresh end-to-end test.

## 5. Full-schema import contract

Preserve the old fixed fixture importer exactly as a regression client. Extract only the transport/state-machine pieces needed by a new `full_restore` module: writer READY/PRECOMMIT nonce and PID/backend-start/xid binding; target birth/locks; durable attempt and commit-intent; one stdin owner; cancellation serialization; no reconnect/replay; postcommit readback; exact quarantine. Fixture budget stays 65,536 bytes. No generic arbitrary-SQL public API results from the extraction.

Use a pinned full-schema contract built once per reviewed application migration set from an independently created empty migrated PG18.6 fixture. Check in canonical schema/TOC/column/ACL expectations with SHA and migration fingerprint. The contract enumerates **every** table (including `_sqlx_migrations`), column/order/type, schema object, constraint/index, function definition/SECURITY DEFINER/search_path, trigger, owner and grant. Unknown schema objects or changed schema SQL are rejected. Normalize only reviewed volatile TOC numeric IDs, source database/archive metadata and the matching restrict key; do not remove arbitrary lines/comments or strip SQL by keyword. The contract must be generated with the actual fixed PG client before accepted code can import data.

For TOC entries, normalize only the archive dump ID and the per-instance object OID; preserve the catalog OID and complete object descriptor. Capture the full custom archive with owners/ACLs, then independently capture both the fixed no-owner/no-ACL decoded SQL and the owner/ACL-preserving schema view. Public role observations contain only reviewed non-sensitive flags/memberships; never capture password catalogs or role configuration. The generated contract records its actual producer/source/build/image/migration provenance. That capture proves contract content; it does not grant source capture, target admission or backup publication authority.

Task4 uses a focused acceptance helper for exactly `full-schema-contract`, `full-schema-altered` and `full-copy-edge-data`, with success class `REAL_PG18_SCHEMA_CONTENT_NOT_RESTORE`. Its independently created PG18 fixture runs the genuine same-source migrator; it has no source Broker/DRAIN/registry or restore target. Reuse the immutable package verifier, fixed compiler/materializer and owned-resource/log primitives. Verify source/build/image/container/client/migration/binary/original-output joins, then confirm exact PG stopped with no active exec, its internal network empty and all volumes retained. Failures remain unusable and cannot be upgraded by read-only verification or replay.

The management content decoder is the fixed local `/usr/lib/postgresql/18/bin/pg_restore` from the pinned PG18.6 runtime, with exact SHA/version and a held verified ordinary file. Root-owned mode0755 is acceptable when neither the file nor its root-owned ancestors are writable by group/others. Use cleared environment, frozen archive stdin and only fixed offline argument sets; no caller path, shell, PATH lookup, connection options or target DB. Retain descriptors/spools until the exact native child is killed and waited after cancellation. Reaping a Docker CLI alone is not proof that its in-container native process terminated.

Freeze and verify the complete dump and decoded SQL into private no-follow spool files before any target DB write. Run fixed `pg_restore --file=- --no-owner --no-acl --exit-on-error`, validate exit, TOC and whole decoded stream. Full restore matches fixed schema chunks and permits variable data only inside enumerated `COPY public.<table>(exact columns) FROM stdin` frames. COPY text payload is data; exact `\\.` terminates a frame and the next byte must resume the expected fixed schema/COPY grammar. Strings containing SQL, newlines, backslashes or psql commands must round-trip as COPY escapes, never reach a SQL or command position. Reject alternate COPY destinations/options, large objects, extensions, sequences/setval not present in the contract, transaction commands, reconnection, altered function bodies or unrestrict position. Reorder whole validated COPY frames into contract order if independent TOC numbering changes; never rewrite field data. Feed only frozen checked descriptor ranges to the writer.

Apply exact trusted owner/grant recipe under the same writer before PRECOMMIT: database roles are independently provisioned with private credentials, validated against roles.json; public schema owner remains pg_database_owner with learning_admin as the database owner, its exact owner/ACL catalog is checked against the independent PG18 fixture, and runtime remains disconnected, SECURITY DEFINER ownership/ACL/search_path match source contract. Do not replay passwords or arbitrary role DDL from dump. `--no-owner/--no-acl` is safe only because exact roles/ownership/ACL reconstruction and catalog equality are mandatory. The clean target cannot first be migrated outside this transaction: schema, historical data, constraints, indexes, triggers, migration rows and trusted ACLs all become one atomic import.

The existing target initdb fixture creates only learning_admin and NOLOGIN learning_runtime; the validated source recipe requires **three** roles, adding learning_auth_lock and the admin membership (NOINHERIT membership, SET true, ADMIN false), plus exact source role flags/connection_limit. Add a dedicated reviewed full-restore provisioner/initdb recipe: verify package and non-sensitive role recipe first, provision cluster-level roles through separate private superuser credentials, then issue the fresh empty-target birth/pin. Runtime can retain the recipe's LOGIN flag while database CONNECT remains revoked. learning_admin stays NOCREATEROLE; the writer cannot improvise role changes. Legacy target fixture/birth behavior remains separately testable and is not silently altered. Final catalog checks cover all three roles, membership options and object ACLs. In particular `migrations/0001_content_core.sql:51–68` temporarily grants schema CREATE to learning_auth_lock, assigns `lock_space_grant(uuid,uuid)` to that role, then revokes CREATE: reconstruct this fixed ownership sequence inside the writer transaction and prove the final CREATE denial, rather than making every function learning_admin-owned.

Full-stream bounded profile is separate from fixture profile: dump <=1 GiB; decoded spool <=4 GiB; TOC <=4 MiB/100,000 entries; one COPY row <=64 MiB; copy buffer 64 KiB; total decode/import deadlines 900 s each; READY/PRECOMMIT receipt waits 10 s; stdout/stderr protocol channels 8 KiB each; cleanup writer disappearance 5 s and exact-stop confirmation 15 s. Overflow rejects before target writes where discoverable. These are explicit initial restore capacity limits, not new limits on original-asset bytes or claims of tested scale. Keep all existing fixture deadlines and budgets unchanged.

Normal `restore_complete_backup` accepts only CompleteBackup. Private `#[cfg(test)]` fresh-local adapter may produce a nonconstructible local rehearsal input only from newly captured enrolled SourceLocalPin plus current batch source/build proof; it shares package/schema/target/protocol checks and uses a distinct candidate attempt capability. It cannot return CompleteBackup, a production preflight permit or a usable marker. Full success still stops the candidate exact target and preserves all volumes/evidence. No old local pin replay.

## 6. Recovery normalization and validation

First independently compare all imported table rows and schema facts with source capture evidence before recovery modifies jobs. Read-only, per-table primary-key-ordered canonical row hashes cover every table, not just counts; identify intentional volatile fields explicitly and do not exclude arbitrary content. Asset index must match all restored ready rows and target originals must be rehashed; verify references and runtime-visible historical/current reading behavior and denials.

Then use a new management-only, isolated transaction for job normalization. Join job/job_outbox and durable snapshot result/request records. Preserve IDs, idempotency keys, attempt counts, checkpoints and terminal receipts. Clear **all** running lease tokens/expiry values regardless of source deadline. Integrity jobs with remaining budget become retry_wait; at 3 attempts become failed. Set a fixed recovery error class and deterministic test clock. Old renew/checkpoint/succeed/fail tokens must all fail. Nonrunning rows already lacking tokens remain valid. No migration or weakened business trigger is needed for allowed running-to-retry/failed/cancelled transitions.

Snapshot side effects require read-only inspection of registered source export artifacts/result receipts, never a caller enum asserting no effect. Confirmed no-effect work can retry within existing max 3. Already committed effects retain matching DB receipt and prevent re-publication. Unknown/conflicting effects keep their full imported row snapshot in a private recovery hold record, move nonterminal work to an existing unclaimable terminal state (`cancelled` with recovery error class), clear leases, and keep the entire target unusable until explicit management reconciliation. Do not invent a new job status or reset attempts. Succeeded snapshot receipts whose external derived files are absent are also held; do not silently declare them usable or regenerate and publish an external effect. This may deliberately prevent one rehearsal fixture variant from passing usability; the clean no-effect/satisfied-receipt variant must pass the recovery validation barrier.

Rebuild actual existing derived state only. PostgreSQL indexes come from validated schema import. Verify `asset_integrity_result` source/digest contracts and exercise current runtime read projections. Current code has no preview/search generator; record those as absent/not applicable to P0 rather than claiming a worker rebuilt them. Snapshot export delivery is a real existing derived/external surface and must be included in the reconciliation barrier. Any rebuild/reconciliation failure leaves an internal inaccessible recovery state.

After full row/schema/asset/lease/permission validation, write a durable `RecoveryValidation` receipt bound to attempt, manifest, recovery-delta and exact target identity. The normal complete-backed path may produce opaque `RecoveredInstance` eligibility, with runtime still disconnected until explicit management activation outside current production scope. Candidate path writes only `FULL_RESTORE_REHEARSAL_PASSED_SINGLE_HOST_QUARANTINED_NOT_COMPLETE`; it never grants runtime access. Receipt sync or commit outcome ambiguity makes the target unusable and unreplayable.

## Appendix A — Task1 exact registry and protection contract

This appendix defines the initial format, not implementation bodies. All new JSON uses UTF-8, recursively lexicographically sorted object keys, compact separators, no trailing LF/BOM, no extra/duplicate keys, and JSON integers (not floats/bools) for counts/versions/dev/inode. Strings use serde_json-compatible escaping without optional ASCII escaping. UUIDs are canonical lowercase RFC4122 v4; digests are lowercase 64-hex; paths are canonical absolute POSIX without empty/dot/dotdot/NUL components. UID is 0; mode is the numeric permission bits (`448` for 0700, `384` for 0600). Records are private ordinary single-link files; directories are no-follow root-owned 0700. The common `FileRef` shape is exactly `{path,size,sha256}`, relative normalized path, size bounded before reading. All roster arrays sort by the named UUID; filenames sort bytewise. Duplicate UUID/path/dev-inode enrollment and aliased roots are rejected.

### A1. Layout and exact keys

```text
/var/lib/knowweave-c4/registry/    # held original directory
  authority.json                 # immutable, <=4096 bytes
  registry.lock                  # precreated ordinary 0600 file; never replace/unlink
  generations/00000000000000000001.json ...  # contiguous 20-digit positive u64
  roots/<enrollment_id>.json      # immutable <=16 KiB
  groups/<group_id>.json          # immutable <=16 KiB
  protection/<source_group_id>/<backup_id>/
    00-pending.json
    asset-index.json              # only after full catalog known
    10-catalog.json
    20-retained.json              # only verified published pin
    30-abandon-ready.json         # optional explicit abandon path
    40-abandoned.json             # optional durable terminal observation
  staging/<v4uuid>/               # all publication temporaries, same device
```

No new marker appears inside a legacy `.control`, local-pin root, `.sealed`, asset or asset-staging tree. `staging` is part of registry only; it does not grant permission to modify existing business staging files.

| Record | Exact top-level keys and value contract |
|---|---|
| `authority.json` | `format_version=1, capability="backup_registry_v1", deployment_id, registry_path="/var/lib/knowweave-c4/registry", registry_dev, registry_ino, lock_dev, lock_ino, directories, initial_generation=1, initial_generation_sha256`. `directories` is exactly an object with keys `generations,groups,protection,roots,staging`; each value exactly `{dev,ino}`. Registry/lock and all metadata directory identities must equal held descriptors on every open. |
| `roots/<id>.json` | `format_version=1, capability="backup_root_v1", deployment_id, enrollment_id, group_id, kind, path, dev, ino, uid=0, mode=448, enrolled_generation`. `kind` is one of `source_assets,source_staging,source_control,local_pins,backup_destination,destination_evidence`. No root marker field. |
| source `groups/<id>.json` | `format_version=1, capability="backup_source_group_v1", deployment_id, group_id, database, database_oid, system_identifier, source_binding_sha256, application_commit, application_build_sha256, roots`. `system_identifier` is canonical positive decimal string; OID positive u32. `roots` exactly `{assets,staging,control,local_pins}`, values enrollment UUIDs referring to matching root kinds. |
| destination `groups/<id>.json` | `format_version=1, capability="backup_destination_group_v1", deployment_id, group_id, destination_host_id, destination_storage_id, roots`; roots exactly `{destination,evidence}`, enrollment UUIDs. Host/storage IDs identify reviewed domain facts; they do not establish independence themselves. |
| `generations/<n>.json` | `format_version=1, capability="backup_registry_generation_v1", deployment_id, generation=n, previous_generation_sha256, roots, groups`. Previous is null only for generation 1. Each roster array contains exact `{id,sha256}` entries sorted UUID ascending, unique. Roster is complete and monotonic: next generation may append enrollments/groups, never remove/replace IDs or change existing record hashes. Highest **contiguous valid** final generation is authoritative; any gap/malformed/unreferenced final record rejects the whole snapshot, not fallback to an older generation. |

Initial issuer creates the fixed root/metadata dirs/lock, opens all handles, observes identities, writes/syncs immutable root/group records and first generation, then writes `authority.json` last through no-replace rename; sync both source/destination parents and read back. Until authority is durable and all exact entries validate, normal APIs refuse. Authority is never updated to follow a substituted root. Record files added without a final valid generation make the registry incomplete; operations do not infer enrollment from loose files. A later enrollment uses the same nonblocking lock, stages new records, syncs them before publishing the next generation commit, syncs both parents and verifies all bytes. On rename-visible/fsync-error, report ambiguous failure; no release/publication in that invocation. Reopen may only use a fully validated, resynced contiguous generation and must still respect original source-terminal ambiguity. No automatic repair, overwrite, rollback, deletion or registration of loose records.

The provisioner never reenrolls an existing group/root for a new inode or build. Such a deployment is a distinct group with fresh roots/UUIDs and cannot absorb old attempts. Future generation growth above 128 is an explicit capacity error; compaction/retirement is outside this task.

### A2. Attempt record keys and commit order

Every attempt JSON record has exactly these common keys plus the stage-specific keys below: `format_version=1, capability="source_protection_v1", deployment_id, group_id, backup_id, registry_generation, registry_generation_sha256, source_binding_sha256, application_commit, application_build_sha256, state, previous_sha256`. Every referenced root comes from the group captured at `registry_generation`; all existing enrollment hashes must remain present unchanged in the current generation. Each JSON record <=16 KiB. `asset-index.json` is the existing canonical backup index bytes, not a new index format.

| File/state | Additional exact keys | Required predecessor/meaning |
|---|---|---|
| `00-pending.json` / `capture_pending` | `roots` exactly the source group's four-root object | previous null. Establish before source journal creation, REVOKE or dump. Pending with no catalog means protect all bytes/no reconciliation candidates. |
| `10-catalog.json` / `catalog_durable` | `asset_index` FileRef with path `asset-index.json`; `logical_asset_count` | previous SHA of 00-pending; index fully written/synced/parsed before record. Catalog is all ready rows under drained source. Manifest not yet required. |
| `20-retained.json` / `retained` | `asset_index_sha256, manifest_sha256, sealed_name, sealed_dev, sealed_ino` | previous SHA of 10-catalog. `sealed_name` exactly `<backup_id>.sealed`; full pin/source files verified, same manifest/index. Must be durable before GRANT; finish may create it only from a verified already-published matching pin. |
| `30-abandon-ready.json` / `abandon_keep_all_ready` | `abandonment_ready_sha256, source_journal_sha256` | previous is latest existing 20/10/00 record. Link verified existing lifecycle ready/journal before abandonment GRANT. This does not convert early/pending state into a finite key set: protect-all remains. |
| `40-abandoned.json` / `abandoned_keep_all` | `abandonment_terminal_sha256` | previous SHA of 30; write only after existing abandonment terminal is fully durable/read back. No loss of any protection, no `Released`, no completion eligibility. |

For the first pending record, assemble the entire `<backup_id>` attempt directory under registry staging, file+directory fsync, publish via no-replace rename into already provisioned `protection/<group_id>`, sync both parents/readback, then permit source mutation. For later catalog/pin/abandon records, create a fresh staging transaction directory, fully write/fsync all new files, publish data file before referring record through no-replace rename and sync both parents. ### B1.5. Publication return, later historical read and new authority are separate accounts

Preserve the current v2 historical readers' acceptance of legally complete signed bytes. They do not consume the original P syscall return/ACK and cannot prove that a previous fsync, verification or reply returned success. The failed/unknown original invocation must not be credited as a normal first-publication success merely because a later read accepts complete signed residue. Later reader synchronization does not repair the original P return. No such read creates a new signature, receipt write, replay or reconstructed authority.

| Failure window | Original invocation/authority | Possible retained bytes and later read boundary |
|---|---|---|
| Before final permission | Pending revocation/error/EOF/timeout wins: Failed; missing reply leaves S HOLD | Sealed/evidence intent/terminal may exist; none reconstruct first-signing permission |
| After permission, before signature | Only original Consuming action may proceed; local error/deadline/unwind: Failed | Fence/evidence remain; no new process may consume the old decision |
| After signature, before receipt rename | Failure: Failed; no witness/success exposure | Signature may be in memory/staging; staging is not a final receipt and cannot be moved to complete the call |
| After rename, before parent sync | Visible rename is not natural parent-sync success; error remains Failed/HOLD | Complete signed final-name bytes may already satisfy unchanged historical readers; that does not prove original sync or normal first-publication success |
| After parent sync, before final verification | Sync success is not verification success; local error/deadline/unwind: Failed | Later complete-byte read may accept but cannot retroactively establish original verification success |
| After final verification, before complete reply | Only all natural action success allows Committed; lost reply leaves S HOLD | Historical destination-only read remains possible; do not re-sign/re-publish or rewrite the original caller's unknown result |

Requiring every future reader to reject any complete signed residue from a failed invocation would be a different, unadopted historical-reading/commit-proof contract. This adoption does not impose it or change v2 to pretend to prove past returns. Existing destination-only full recovery still requires the captured protection proof and its linkage, never historical live S access. Bare-v2 low-level reading is not promoted to new full-recovery authority.
