# 11 分线交付与验收计划

Task9 沿已批准规范继续。浏览器首用已在独立分支完成 B0/B1。每条线分别记源码、运行结果、证据覆盖和停止条件。完成按可观察交付结算，进度以当前门和下一项依赖呈现。

## A 线 · Task9 与 P0-C4 收口

| 顺序／状态 | 本次唯一要证明的结果 | 下一步准入与边界 |
| --- | --- | --- |
| A1 · 已封存，待审批 | 用新干净 S1 副本跑修订首启。验证 2 GiB 容量门、迁移、三种 peer 许可与四种拒绝、无 TCP、精确停机及 QEMU 资源证据。 | 实际重跑需明确批准。核对临时 unit 的 `TasksMax=128`，有效样本峰值低于上限、触限事件为零且无该 unit 的内核拒绝。任何缺项进入 HOLD。 |
| A2 · 依赖 A1 | 在 S1 的全部门通过并停机后，才投送 S2 介质；同等标准独立验证 S2。 | S1 未通过时，S2 不启动。既有 HOLD 只读封存。两案通过才使用各自实际身份构造后续 binding。 |

| A5 · D1/RA 与规定负例 | 在 S1→V1 正常首签与发布并打开 CompleteBackup，RA 用同一完整恢复引擎验证全表、授权、原件、任务、效果及阅读字节；规定 S2/V2 中断案证明 prior complete 逐字保全。 | 新资源和实际跨机首签、正常恢复须批准。两个源视图独立，S1 fence 按计划持续保留。 |

## 缩短验证往返

1. 每张待办卡只记录一个可证伪结论，并具名写出“输入／进入条件／成功原件／失败留存／下一门”。已有决定采用批次及其冻结文件为准。
2. 在申请现场变更前合并可复用的只读检查。记录输入哈希、实际身份、容量、挂载和网络；有时间敏感的值标明观察时刻，执行前复查。
3. 每个案内将“测试通过”和“证据足够采信”分成两项。优先收齐与本次结论相关的原件；外层 exit 0、摘要或历史同字节桥分别记账。
4. 每周或关键门有结果时更新单一状态。记录阻塞原因、停留天数、最后新增的原件和下一次决定。首轮按相同口径计数“准备→审批→运行→独核”，下一轮才比较周期。
5. 变更方案优先处理实际失败点。需要重跑时创建新批次，批准已封存的动作。保留旧失败和来源；没有适用的源/二进制或环境证据时将条目标为待补。
