## 1. 建议用户裁决的实质变化

推荐继续评审的候选是：**原 S 完成最终核对和持久负 fence 后，只向本次仍活着的原 D 尝试发出一次固定最终决定；D 可在严格前提下消费该决定一次，不再要求证明远端 S 在每一次后续物理写入瞬间仍活着。**

网络无法证明这个瞬时活性。S 最后决定发出后、D 尚未物理提交时，S 可能死亡，D 也可能尚未观察到死亡。心跳、短 TTL、多次确认或再加一轮 ACK 都不能消除最后一条消息之后的窗口。本文不把负 fence、认证消息或最后一次源核对称为 S 持续活性的证明。

这与现准备规格“最终提交前的对端退出、断线或取消关闭新发布”的无条件表述存在实质差异，也改变了 Appendix B 中由活 S 在发布前持有并核对保护的跨机承接方式。**只有用户明确采纳准确的例外范围、规范修订并独审通过后，才能进入 R2b；Task9 原本留有异机集成门，不等于已隐含批准这一选择。**

| 事项 | 现合同边界 | 本文建议，尚未采纳 |
|---|---|---|
| S 生命周期 | 新发布依赖原 S 操作和发布前保护核对 | 原 S 的最终选择前保持原上下文；此后用负 fence 保持指定保护不变量，不再声称物理进程持续活着 |
| 撤销截止点 | 跨机准确截止点尚未采纳 | D 本地 `Pending → Consuming` 是最终许可的胜负点；不是 receipt 持久提交成功点 |
| 新发布入口 | fresh-lease 路径继续拒绝 | 仅新增经审的 D 原 receiver 内部入口，结合原 D 成功和本会话最终决定；旧入口不放宽 |

## 2. S、D、C、P 的不可替换前提

S 是原管理 actor，继续持有原 `SourceAdmission`、registry lease、共享累计 scan budget、源构建绑定、enrolled roots、保护快照和包描述符。不能复制这些字段、刷新预算或另取相同 ID 的 lease 来冒充原操作。`Arc::ptr_eq` 等旧本地约束不删除，也不跨机传递或伪造 Arc。

D 是本次固定 receiver 原进程，持有其本地原 lease、目标与证据根、原 `OperationAuthority`。只有 D 的 Admit、Prepare、Stage、BeforeRename、Rename、ParentSync、FinalReadback、TerminalWrite、TerminalSync、TerminalReadback、FinalRecheck 十一步及 outcome 全部自然成功，才可能登记原 D 内存成功状态。unsigned terminal、完整校验和、后续 resync/readback 或重连不能替代这些返回。D 进程或原操作一旦丢失，新进程没有继承资格。

C 是待审的认证与状态衔接，不是把 S 快照反序列化成 D 的本地 lease。它须将原 S 身份和活操作、本次双方新挑战、方向/序号/协议域、完整 transcript、backup/attempt/proof/manifest/source-control、source group/build、registry generation 和各自 enrolled roots 绑定到同一个 D 尝试。各主机只核对本地持有根；跨机 `st_dev`/inode 大小或相等关系不证明独立故障域。

P 是拟新增的 crate-private 最终 publisher，只能由 D 原 receiver 的已准入路径到达。不得调用旧 fresh-lease publisher 来承接权限，不接受调用者提供的 `authorized=true`、成功对象或可序列化 permit。原 v2 manifest、statement、witness、receipt 和严格证据文件集合保持；新的管理记录不能擅自塞入这些固定集合。

普通 SSH 账号、root 文件模式 `0600`、自报 build hash 或一张签名均不足以证明原 manager。推荐源管理认证身份与 D 备份签名 key 分离，并由另审的 root 管理部署合同约束固定启动、实际二进制、实例和 key 使用入口：

- 核对安装二进制及可信启动路径，拒绝可替换程序、插件、任意命令或环境注入；明确宿主 root 的可信假设，不能声称抵抗任意 root 改写。
- key 只能供经审原 actor 的固定认证函数使用；该函数从原持有对象派生消息，不接受任意待签字节、调用者声称的 lease/阶段或任意路径。
- 若采用窄 broker，须证明调用者身份、原 actor 状态和实例绑定，不能仅凭 PID 字符串、普通 IPC 请求或“我持锁”布尔值代签。broker 本身的权限变化另审。
- D 的信任明确约束受审源部署/构建及身份；D 自身也须使用真实安装并核验的固定 receiver。挑战来自各自原实例，不由调用者指定旧值。

这只是身份设施的约束建议，不配置或选择实际 key 文件、sudoers、服务权限或二进制。

管理身份与自动传输身份还须分开。2026-10-26 的只读安全元数据盘点返回：目标管理账户属于 docker/sudo/lxd 组，可访问本机系统 Unix Docker socket，Docker context 无远端覆盖，daemon info 成功且 SecurityOptions 未报告 rootless，数据目录为系统目录。这里只报告这些观察，不代替独立 daemon 身份审查作绝对 rootful 判定；没有运行 root 容器、读取 key、实施 root 攻击或验证恶意管理员防护，也没有执行 sudo 或改动权限；固定安装根仍不存在。

Docker 官方说明 docker 组授予 root-level 权限，这是官方权限模型，与上面的点时元数据观察分别记账。[Docker Linux post-installation：Manage Docker as a non-root user](https://docs.docker.com/engine/install/linux-postinstall/#manage-docker-as-a-non-root-user)。因此，管理账户不能被默认当作最小权限传输身份。推荐 C 包另审非交互、受限 principal 和固定命令调用，不默认将管理 SSH 密码或广泛 Docker 访问权交给 S。任何新用户、SSH 公钥、forced command、sudoers、源管理认证身份或已有身份权限调整均列出准确变更并另批，当前不创建或配置。

## 3. 推荐时序与不可回退裁决

下列顺序是新合同建议，不是现有代码已经完成的流程：

1. S 在原操作下冻结捕获、持有包对象并开始新会话；D 完成真实根准入、独占 backup-ID 残留检查及双方挑战认证。数据流和认证均有固定预算、期限和严格终结规则。
2. D 独立读取并核验全部包与捕获证据，按原十一阶段及 outcome 完成证据提交。此时只有原 D 内存成功，尚无新收据，也不对外提供 witness。
3. S 保持原锁、原预算及原对象，独占发布、同步并以持有 FD 回读负 fence；再次核对精确保护状态及 fence 绑定。任何失败或不确定都不选择最终决定。
4. 原 S 在本地串行点只选择一次 `SOURCE_FINAL_DECISION`。固定消息绑定该 fence、原操作和本次 D 挑战/尝试/证据；它只对本活会话有意义，不是可保存后交给新 D 的 permit。S 不因发出消息或收到传输 ACK 而报告备份成功。
5. D 在其原串行裁决内检查全部已到达的拒绝条件：原 D 成功仍有效、完整可信 S 最终消息及本次 C 均匹配、挑战未消费、保护连续性的可信来源已成立、无此前已观察的取消/EOF/错误/超时、当前期限尚有效。仅全部满足，才 `Pending → Consuming`。
6. 进入 `Consuming` 后只进行该次内部 action：在最终许可后产生 v2 签名，排他写入 receipt staging、同步、禁止覆盖 rename、父目录同步、完整最终验证。原 D 权限和最终消费状态的撤销/使用共同排序；不能用两个没有排序的锁，也不能递归锁定同一 context。
7. 全部本地操作自然成功后才 `Consuming → Committed`，此时才可生成对外成功结果。任一本地写入、同步、验证、期限检查失败或 unwind，进入 `Failed` 并失效相关新签名/发布资格，保留残留。`Failed`、`Committed` 均不回到 `Pending`，不允许再签、再发布或同 ID 新尝试。
8. S 仅收到本次完整且经可信核验的 D 成功结果后，才能报告其观察到的正常成功。结果缺失或不能核验则 HOLD；不自动重连、重发最后消息、换 nonce 重试或让新 D 接纳旧决定。

`Pending → Consuming` 是**许可不可撤回点**，`Consuming → Committed` 是**本调用的目的端自然完成点**，两者必须分开。原 `finalize_use` 不是这个新增状态机；其原行为不能被函数名称替代证明。

在 D 仍为 Pending 时，已经观察并进入同一裁决的取消、EOF、错误或超时必须使撤销胜出，拒绝消费。取消和消费竞争只有一个本地排序；不能用 S 与 D 的时钟比较声称共同原子提交。

如果完整可信决定已到达，原 D 在有效期限内先进入 Consuming，随后才观察到远端死亡、取消或连接中断，建议允许该次已获许可的本地 action 继续；迟到事件不能追溯夺回许可。它仍可能因自身错误、期限或 D 退出而失败。这个规则也属于待审批的时序调整，不得藏在“处理网络错误”的实现细节中。若操作系统终止 D，内存 authority 随进程丢失；只保留当时已有磁盘结果，不由新进程续做。

## 4. 负 fence 只保持保护连续性

建议新增另行准入的固定管理 namespace，位于旧严格 package/evidence 文件集合之外。负 fence 是持久拒绝条件，不是新首签或发布的正权限。D 对 fence 的可信认识来自经审原 S actor 的实现和本次认证关系；远端自报 fence hash 本身不证明其实际持久化。

首次发布须在原 S 锁下独占、禁止覆盖，完成文件及必要父目录同步、持有 FD 回读和根身份重核，随后才允许最终选择。发布失败、可见但同步结果不明、损坏、未知版本、namespace 缺失/替换、扫描超限等都关闭最终选择和相关后继变更；不能把不确定视为没有 fence。

其后所有相关写入方均必须在共同串行边界内发现并遵守未关闭 fence，至少覆盖：

- 使原 snapshot 的 records、引用/保护计数、所关联 generation 或 enrolled root 身份失效的变更；不仅是 GC、删除或释放。
- 旧构建、替代管理入口、重新登记、generation 变更、根迁移、恢复和管理修复。未证明不影响上述不变量的相关管理变更默认拒绝。
- 启动、升级和重新安装后的检查；不能因原 S 死亡、锁释放、版本变化或另建 registry 而遗忘 fence。

原 lease 依赖完整 registry generation/metadata 时，一个 fence 可能阻止其他 source group 的注册、代际更新或根调整。不能先宣称“只影响本备份”：必须列出全局影响，或另外证明更窄的等价不变量并独审。也不能自行把普通业务数据库所有写入冻结；实际受阻范围以受审保护观察和管理入口为准，未证明的范围不能承诺不受影响。

每次操作仍使用原累计预算。新增 fence 的条数、字节、读取和保留空间须有固定上限及计费规则，不能获得一个不计入上限的旁路扫描。UNKNOWN 长期保留可能导致容量耗尽或管理阻塞；达到上限继续拒绝，不丢弃旧 fence、不刷新预算、不按 TTL 自动释放，也不自动重试。

可继续评审的最窄关闭资格是：仍活着的原 S，在原 lease 和原持有 fence 对象下，收到本次 D 完整成功结果，且结果核验合同和所需成功证据已独核后，追加独占、同步、可回读的关闭记录；保留原 fence 和历史，不删除或覆盖它们。原 S 若已退出，新进程不能仅从磁盘、成功摘要或历史 receipt 重建该关闭资格；解除只能留给以后另行受审的管理流程。关闭失败或不确定继续保留负约束，不追溯否认已真实完成的 D 结果，也不再发布 receipt。

上述关闭条件目前也未实现或采纳。若实施初版不能证明它，可以继续保留 fence，但须明确其可用性代价。可信管理员和所有相关写入方服从约束、固定 namespace 不被绕过、文件系统持久语义成立都是必要假设；fence 不防御任意 root 删除、存储回滚或未受控写入，也不证明 S 还活着。

## 5. 六个失败窗口与结果分账

以下表格假定同 ID 既存残留已在准入时拒绝；它描述本次尝试，不允许覆盖已有包。每个窗口都保留实际原始调用结果，不凭后来的观察改写过去。

| 故障窗口 | 原调用及内存权限裁决 | 可能存在的字节 | 以后目的端只读重开与禁止事项 |
|---|---|---|---|
| 最终许可前 | 已观察的错误/取消/EOF/超时拒绝消费，Pending 进入 Failed；S 发过决定但未获结果时只知 HOLD | 可能已有 sealed 包、证据 intent/terminal；没有本次许可产生的签名或 receipt | terminal 不授首签；无完整 signed receipt 不走正常 CompleteBackup 重开；不得同 ID 补做 |
| 许可后、内部签名前 | 已进入 Consuming 不因迟到远端事件重新开放；本地错误/期限/unwind 使 Failed | 原证据和负 fence；尚无签名 | 不从 fence、决定或证据重建消费资格；S 未收到完整成功仍 HOLD |
| 签名后、receipt rename 前 | action 失败则 Failed，不输出 witness 或成功对象 | 签名可能只在内存，或存在含签名的 staging；最终 receipt 名尚未发布 | staging 不被当作 final receipt，也不搬运/补 rename；签名不能转交新进程续发 |
| receipt rename 后、父目录同步前 | rename 可见不等于同步自然成功；失败返回及 Failed 不被后来读取改写 | 最终 receipt 名下可能已有完整已签字节，持久性未知 | 现 v2 reader 可能接受这些完整字节；这不是当时父同步成功的证据，不计正常首发正例，不补写或再签 |
| 父目录同步后、完整最终验证前 | 同步返回成功仍不能替代最终验证；验证错误/期限/unwind 使 Failed | 可能已有已同步 receipt、完整 package/proof，也可能存在后来检查发现的变化 | 以后若现 reader 的全部读取合同成立，可能只读接受；不得由此追补当时验证成功或原调用成功 |
| 最终验证后、完整回复前 | 仅 D 全部自然成功才 Committed；若回复丢失，S 仍 HOLD，不能自动判断是否到达该点 | D 可能已有真实完整 receipt 和提交结果；仅“验证做过”不等于其返回已被记录 | 可按既有目的端合同只读核验历史字节；不能重发签名/receipt、新消费，或将 S 的未知返回改成原调用成功 |

必须分别记录三件事：**原调用是否自然成功返回；以后目的端 reader 实际是否接受；是否存在新首签/新发布资格。** 前两项可能不同，第三项不能由前两项重建。

现 v2 receipt 的签名覆盖既定 statement，receipt digest 与完整字节重读不能记录或证明过去每一次 `fsync`、最终验证或发送回复的返回。完整已签残留在后续读取时可能满足现 reader；本文不声称可以仅凭原 v2 将它与“当时全部调用自然成功”区分。更改版本号或加一个普通 checksum 也不会自动证明这一事件事实。

推荐保留既有历史 reader 合同，诚实报告这类读取现象，但不把已返回错误的调用、一次 later-readback 或历史读取接受记为 Task9 正常首发成功，也不据此授补签/补写资格。若用户要求“任一次同步/验证失败后，任何未来 reader 都绝不能接受可见已签残留”，这是另一项需设计并采纳的历史读取/提交证明合同，当前方案不能承诺；届时保持入口关闭，不在此文擅改 v2 或 reader。

这与当前源码一致：`complete.rs:470–481` 在 receipt rename 后才做父同步、完整验证并返回；`ErrorFence` 关闭内存权限，不删除 receipt 或持久化 P 的失败裁决。历史 reader `complete.rs:282–319,503–505` 不读取原调用返回或 ACK；更强的捕获证明入口 `destination.rs:808–826` 也有意采用历史完整包路径而非 `read_authorized`。因此，本推荐明确保留当前 reader 对合法完整已签字节的既有接受行为，不要求其拒绝所有失败调用的残留；调用方 UNKNOWN/HOLD 和历史只读接受可以同时成立。

历史完整包的恢复仍只核对 D 的 package、receipt、trust 及捕获证明，不打开历史 S registry/DB/assets/pins，不比较历史 S inode 和 D 副本 inode。旧 bare-v2 的低层读取不扩大为缺少捕获保护证明的全量恢复资格。

## 6. 推荐与保守备选

推荐供审的是第 3–5 节的有限最终决定方案：明确接受最后消息后的远端死亡窗口，以全程强制负 fence 保持指定保护状态，D 原操作一次消费，结果未知不重放，历史读取与原调用分账。这能保持公共 v2 和旧本地拒绝路径，但新增 C/P authority 与持久管理约束，仍须规范及用户批准。

保守备选是维持原严格要求：S 必须活到 D 最后物理写入且可在此前撤销。仅 SSH、心跳、认证 key 或多轮 ACK 无法证明它，因此异机入口继续关闭；另行提出具备明确故障假设和裁决语义的可信协调设施再审。不能把“加一个 broker”本身当作解决跨机死亡窗口的证明。

没有负 fence 而仅靠原 S 尽量保持在线，不是本推荐的等价简化；它既不能消除死亡窗口，也不能保证 S 死亡后后继管理操作保持同一保护观察。默认结论仍为未采纳，不能按推荐已经获批施工。

## 7. 最小规范替换文字候选

以下文字仅供审批后定稿，不在本文生效；只拟用于经审 Task9 异机路径，其他 Appendix B/B1 拒绝条件不放宽：

> 异机新发布必须由原 S actor 在原 lease、原累计预算、源构建与根绑定下完成最终核对，并在最终选择前独占持久化经准入的负 fence。负 fence 只维持受保护状态不变量，不产生首签/新发布权限，也不重建已丢失的原操作。其全部后继管理入口、预算和关闭条件须独立受审。
>
> 原 S 仅向本次原 D 活尝试发出一次经认证且绑定双方新挑战、完整请求及证据的最终决定。D 只有在原十一阶段及 outcome 自然成功、该决定及本次 C 全部成立、保护连续性可信且没有先获裁决的错误/取消/EOF/超时时，才可在同一 D 串行边界进入 Consuming。此前撤销胜出即拒绝；此后远端死亡或迟到取消不追溯撤销该次许可。这明确允许 S 决定发出后死亡而 D 尚未获知的窗口，不声称 S 持续活性。
>
> 原 D 仅在 Consuming 内产生内部签名并完成 receipt 排他写入、同步、禁止覆盖发布、父同步和完整验证；全部自然成功后进入 Committed 并才可对外提供成功结果。任一本地错误、期限或 unwind 进入 Failed 并关闭新签名/发布资格。两个终态均无重试、回退、重连续做或新进程继承；旧 finalize_use 不替代一次消费状态。
>
> S 未收到完整可核验成功结果时维持 UNKNOWN/HOLD，负 fence 不自动释放。原调用失败不能被后续 readback/resync 追补为过去成功；现 v2 历史 reader 可能接受完整已签残留，这一只读事实不授新签名/新发布资格，也不计该失败调用的正常首发验收。若要求排除这种历史读取，须另行采纳相应合同，不能声称当前 v2 已具备该证明。
>
> 已真实成立的历史完整包继续按目的端只读重开与恢复合同使用，不依赖源在线；不重签、不重发同 ID，不将 bare-v2 低层读取扩大为新的全量恢复资格。

## 8. 实现前仍须证明的事项

即使用户采纳语义，也不表示这些实现义务已经闭合：

- 原 manager 的可信启动、实际二进制和认证 key 独占使用；D 固定 receiver 的真实来源与安装身份，内部消息的域分隔、挑战、transcript 和防跨会话替换。
- D 的原十一阶段自然返回到内存成功登记的全部错误链；新消费状态与原 authority 的唯一排序、错误/unwind失效，首签不提前外泄；无锁递归或双锁窗口。
- 负 fence 的固定 namespace 准入、独占/同步/回读、所有写入入口与旧构建门控、全局 generation 影响、累计预算、UNKNOWN 保留和窄关闭资格；不能从磁盘恢复正权限。
- 每一失败窗口实际产生的字节、原始 syscall 返回及 reader 行为；尤其不能用日志标签代替真实同步/rename/完整读回。真实断线、进程死亡和撤销竞争需有明确可重复的隔离验证。
- 有界真实 reader 在分配前检查 header/长度、完整 EOF/自然退出、固定总期限和所有包/元数据预算；无权限 framing 准备通过不能替代它。
- 原 API、七份旧源码 pin、公共 v2 和历史 source-unavailable 恢复边界的回归；37 条矩阵内容和未执行状态在真实运行及独核前保持，不凭文档或单测累计信用。
