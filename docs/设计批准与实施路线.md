## 2. 设计基线与技术方向

### 2.1 已确定的系统原则

- 个人长期使用，同一核心系统可用于深度学习、系统工程等不同领域。
- 服务器部署，通过浏览器跨设备访问；原件、结构化内容和派生缓存分开存储。
- 块是最小内容修订单位；稳定身份与不可变修订分离。
- 原文、笔记、图片、想法和猜想连续呈现，个人插入层独立保存。
- 阅读位置、块链接、语义关系、认识审查和学习事实分别建模。
- PostgreSQL 保存权威数据并承担首版关系查询；首版不常驻 Neo4j。
- 正式发布与学习快照固定版本；升级采用范围由明确操作决定。
- 原件保持原格式和字节；JSON/Markdown 是交换或展示形式，不形成第二套可随意修改的权威正文。

### 2.2 技术选择的确认程度

| 层 | 规划选择 | 确认程度 |
|---|---|---|
| 后端语言 | Rust | 用户明确指定 |
| 使用端 | 独立 Web 前端，通过 API 访问后端 | 用户指定方向、总体设计已明确浏览器使用 |
| 权威存储 | PostgreSQL + 原件文件存储接口 | 已批准架构 |
| Rust 异步与 HTTP | Tokio + Axum | Tokio 已用于 P0-A；Axum 仍为后续建议 |
| 数据库访问 | SQLx，参数化 SQL、显式事务和迁移 | P0-A 已采用并验证 |
| 前端框架 | React + TypeScript + Vite | 建议默认组合，用户尚未指定具体框架 |
| API 契约 | 版本化 JSON / OpenAPI；Rust 与 TypeScript 类型映射 | 拟在相应阶段固化 |
| 运行方式 | Linux + Docker Compose，同源 Web/API | 已批准部署方向，具体实例参数在获准实施后落实 |

后端语言与数据模型不再按 Python 方案规划；历史 Python 实验保留为证据。框架选择不会改变块、位置、关系、快照和学习事实的契约。本文和施工单以建议组合描述实现路径，不将建议写成用户已经批准的具体依赖版本。

P0-A 已进入依赖兼容性验证：Rust 工具链、Cargo.lock 和实际测试镜像摘要随验收记录保存。前端依赖在后续阶段锁定；数据库版本与迁移版本分别记录。

以 Attention 为首个领域样例：一个有明确来源的原件、若干知识块、两份复用同块的文档、一个学习单元及个人记录。

1. 在两个原文块之间加入笔记与图片，再在两条个人内容之间插入猜想。
2. 连接两个同源证据和一个反例；端点固定到具体修订，来源运行分组不冒充统计独立性。
3. 修订共享知识块，查看影响和解释路径，只让一份文档采用新版。
4. 另一份文档、旧笔记和旧验收保留；猜想新版不会自动继承旧证据判断。
5. 将一个块拆成两个具有不同稳定 ID 的新块；确认一处位置迁移，不确定项保留待放置。
6. 两个浏览器并发保存时明确冲突，失败一侧保留草稿；历史预览不覆盖编辑中的内容。
7. 导出融合快照，在干净实例核对原件、修订、出现位置、关系和学习事实。

样例随里程碑逐步贯通，不用一次性导入整套课程库验证基础模型。

## 6. 前后端责任与工作区规划

Rust 后端持有授权、校验、事务、版本推进、关系语义和持久化事实。前端持有编辑中的草稿、阅读交互和请求状态；只有服务端确认才显示保存成功。遇到超时或响应丢失时先核实原请求结果，不能换新幂等键盲目再写。

Rust 内部结构不直接作为前端任意可依赖的数据库行输出。API 将使用稳定 DTO；UUID 以字符串传递，错误代码、修订引用、分页和截断语义显式定义。前端不自行推断支持关系的传递性，不把“有新版”直接视为已升级。
