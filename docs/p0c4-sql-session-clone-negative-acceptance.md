# P0-C4 Task 3b: same-identifier wrong-endpoint negative

`--sql-session-clone-negative` is a separate, opt-in mode of the root-only pin acceptance runner. It requires a fresh primary `--batch-id` and `--subnet`, plus a different fresh `--clone-batch-id` and nonoverlapping `--clone-subnet`. Both projects, networks and volumes must be unused against the same initial Docker snapshot. A failed or stopped batch is never replayed. The previous Task 3a batch is evidence only and cannot be a source.

The runner reuses the primary target's reviewed birth, pin inspection and pinned offline Rust builder. Before PG birth, the builder must list exactly one distinct `live_read_only_same_id_wrong_endpoint_negative` Linux test. It keeps the primary running. After checking the pinned PostgreSQL 18 image and the primary's exact Docker ID, it inspects the first physical-replication `host` HBA rule by PostgreSQL 18 `rule_number`. Only an exact `127.0.0.1/32` rule for `postgres` or `all`, with `trust` or `scram-sha-256`, is admitted. Earlier broad rules, malformed records, included files, changed unloaded HBA bytes, insufficient WAL senders or missing replication privilege fail closed. The runner does not edit roles or `pg_hba.conf`. [PostgreSQL 18 HBA rule view](https://www.postgresql.org/docs/18/view-pg-hba-file-rules.html) and [initdb authentication defaults](https://www.postgresql.org/docs/18/app-initdb.html) describe this first-match and default-auth behavior.

For an exact loopback `trust` rule, the temporary helper joins only `container:<primary immutable ID>` and uses no password or passfile. For exact loopback SCRAM, it reads only this new primary's private `postgres_password` file and mounts a 0600 passfile read-only into that helper. The passfile lives under a root-private, batch-specific `/run/knowweave-c4-clone-<UUID>/` tmpfs directory and is removed after the copy, including on ordinary failure. A process kill can leave it in `/run` until root cleanup or reboot; it is never written to durable batch evidence. Neither branch passes a password in arguments or environment.

A pinned-image, no-network helper first creates an empty PostgreSQL-owned data directory in the new volume. A second pinned-image helper shares the exact primary network namespace and runs `pg_basebackup -F plain -X stream` into it. A third helper runs `pg_verifybackup` and rejects `standby.signal` or `recovery.signal`. The copy remains stopped until these checks pass. The runner then creates a separate non-root PG18 container in the clone's isolated network with only that volume mounted, checks readiness, and compares its system identifier and database OID with the primary's sealed birth. It rechecks the primary's exact Docker identity and unchanged `StartedAt` before the wrong-endpoint SQLx test.

Task 1 leaves the distinct ignored Rust test hook deliberately failing closed. Until Task 2 supplies it, the offline builder listing check rejects the mode before PG birth. Task 2 must supply its one-test, one-marker wrong-endpoint assertion before the runner can report `SAME_ID_WRONG_ENDPOINT_REJECTED_READ_ONLY_NOT_RESTORE`. A failure attempts exact-ID stops for every created PG container and records whether each volume exists and is retained; created volumes and evidence stay quarantined. The runner never imports a dump, calls restore or `CompleteBackup`, writes application data, or admits service traffic.

After independent review, a tracked-byte ZIP and exact runner must be separately authorized for a new Linux batch. Before upload or execution, verify the ZIP, manifest and runner SHA-256, the pinned image, both unused UUIDv4 project identities, both unused volumes and subnets, and root-private paths. After execution, verify raw `result.json` and `pin-inspection.json` hashes, no `result.pending.json`, both immutable PG IDs stopped, and both volumes retained. Local Windows tests only cover the runner's logic and mocked Docker boundary; no Linux/PG18 clone has been run by this change.
