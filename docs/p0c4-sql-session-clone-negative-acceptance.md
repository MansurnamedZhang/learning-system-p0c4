# P0-C4 Task 3b: same-identifier wrong-endpoint negative

`--sql-session-clone-negative` is a separate, opt-in mode of the root-only pin acceptance runner. It requires a fresh primary `--batch-id` and `--subnet`, plus a different fresh `--clone-batch-id` and nonoverlapping `--clone-subnet`. Both projects, networks and volumes must be unused against the same initial Docker snapshot. A failed or stopped batch is never replayed. The previous Task 3a batch is evidence only and cannot be a source.

The runner reuses the primary target's reviewed birth, pin inspection and pinned offline Rust builder. Before PG birth, the builder must list exactly one distinct `live_read_only_same_id_wrong_endpoint_negative` Linux test. The issuer records the primary exact container's `StartedAt` from its verified Docker birth snapshot in root-private `birth-evidence.json` before final birth publication. Pin verification checks the value against the current exact container and hashes the evidence bytes. Task 3b reads that hash-covered value after pin inspection and rejects any change through physical cloning; it never resets the start baseline from a later snapshot. After checking the pinned PostgreSQL 18 image and the primary's exact Docker ID, it inspects physical-replication HBA records by PostgreSQL 18 `rule_number`. It skips earlier rules that cannot match `postgres` at `127.0.0.1`, then admits only an exact `host replication postgres|all 127.0.0.1/32` rule with `trust` or `scram-sha-256`. Earlier broad or ambiguous matching rules, malformed records, included files, changed unloaded HBA bytes, insufficient WAL senders or missing replication privilege fail closed. The runner does not edit roles or `pg_hba.conf`. [PostgreSQL 18 HBA rule view](https://www.postgresql.org/docs/18/view-pg-hba-file-rules.html) and [initdb authentication defaults](https://www.postgresql.org/docs/18/app-initdb.html) describe this first-match and default-auth behavior.

For an exact loopback `trust` rule, the temporary helper joins only `container:<primary immutable ID>` and uses no password or passfile. For exact loopback SCRAM, it reads only this new primary's private `postgres_password` file and mounts a 0600 passfile read-only into that helper. The passfile lives under a root-private, batch-specific `/run/knowweave-c4-clone-<UUID>/` tmpfs directory and is removed after the copy, including on ordinary failure. A process kill can leave it in `/run` until root cleanup or reboot; it is never written to durable batch evidence. Neither branch passes a password in arguments or environment.

The runner writes a root-private, secret-free Compose document for the second project and runs `docker compose create --no-build --pull never` to provision its isolated network, empty named volume and stopped non-root PG18 container. It verifies exact Compose project, image, network, volume, stopped state and immutable IDs before copying. A pinned-image, no-network helper first creates an empty PostgreSQL-owned data directory in that volume. A second pinned-image helper shares the exact primary network namespace and runs `pg_basebackup -F plain -X stream` into it. A third helper runs `pg_verifybackup` and rejects `standby.signal` or `recovery.signal`. The clone PG remains stopped until these checks pass. The runner then starts the already verified Compose container by exact ID, checks readiness, and compares its system identifier and database OID with the primary's sealed birth. It rechecks the primary's exact Docker identity and unchanged `StartedAt` before the wrong-endpoint SQLx test. An ambiguous Docker helper creation is resolved by deterministic name; only a fully verified exact helper ID is removed. If verification or cleanup cannot be confirmed, failure evidence records `clone_helper_cleanup: UNCONFIRMED`.

Task 1 leaves the distinct ignored Rust test hook deliberately failing closed. Until Task 2 supplies it, the offline builder listing check rejects the mode before PG birth. Task 2 must supply its one-test, one-marker wrong-endpoint assertion before the runner can report `SAME_ID_WRONG_ENDPOINT_REJECTED_READ_ONLY_NOT_RESTORE`. Birth evidence issued before the `container_started_at` field fails the strict pin check; a fresh batch is required. A failure attempts exact-ID stops for every created PG container and records whether each volume exists and is retained; created volumes and evidence stay quarantined. The runner never imports a dump, calls restore or `CompleteBackup`, writes application data, or admits service traffic.

After independent review, a tracked-byte ZIP and exact runner must be separately authorized for a new Linux batch. Before upload or execution, verify the ZIP, manifest and runner SHA-256, the pinned image, both unused UUIDv4 project identities, both unused volumes and subnets, and root-private paths. After execution, verify raw `result.json` and `pin-inspection.json` hashes, no `result.pending.json`, both immutable PG IDs stopped, and both volumes retained. Local Windows tests only cover the runner's logic and mocked Docker boundary; no Linux/PG18 clone has been run by this change.
