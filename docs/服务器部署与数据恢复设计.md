# 服务器部署与数据恢复设计

已批准设计基线 v0.3 · 2026-09-17 · 配套于[总体设计](学习系统设计方案.md)、[内容分块与存储规范](内容分块与存储规范.md)及[连续阅读与思考块设计](连续阅读与思考块设计.md)

本设计已获用户批准；测试环境与交付安排见[设计批准与实施路线](设计批准与实施路线.md)。批准设计不改变已有实验的失败记录，也不表示正式应用已经部署。

目标是在一台服务器上运行私有学习系统，通过浏览器跨设备访问。首版只有一个学习者，仍按服务器应用管理身份、文件、事务、失败恢复和备份。本文是部署与运维设计，不是已执行的安装或配置。

2026-09-30 整理入口：[当前项目架构](KnowWeave架构设计总览.md)。当前代码与验收状态以新文档及阶段台账为准，以下批准目标和格式示例不表示全部已经上线。

## 1. 推荐部署拓扑

```text
浏览器（电脑 / 平板 / 手机）
                  │ HTTPS，同一站点
             反向代理 / TLS
                  │
          Web 静态资源 + API
                  │
        ┌─────────┴──────────┐
   PostgreSQL            文件存储接口
        │                  │
   数据库任务队列      本地持久卷 或 S3 后端
        │                  │
        └──── 后台 Worker ─┘
                   │
          可选外部来源 / AI 提供方

独立备份任务 → 数据库一致性备份 + 资产清单 + 异机副本
```

起步形态：Linux 服务器、Docker Compose 管理进程，PostgreSQL 保存业务数据，持久化文件卷保存原件。Web/API 可以由一个应用进程提供，也可将静态 Web 独立交给入口代理；它们对用户保持同源，简化登录与访问。

API 与 Worker 复用同一业务代码和版本，作为两个运行角色启动。二者共享数据库和资产接口；页面请求不执行长时间 OCR、整库索引或大文件导出。

首版采用已验收的本地 filesystem 资产卷；S3 或兼容服务仍需实现并单独验收适配器，当前不能直接切换为已支持后端。存储位置由部署配置选择，业务身份不依赖客户端绝对路径。初期无需额外引入消息中间件、搜索集群和容器编排集群。

## 2. 程序模块与项目文件拆分

以下是未来应用的建议结构，与当前 HTML 资料目录分开。现阶段不会按此创建空壳项目。

```text
learning-system/
  apps/
    web/                       # 页面、编辑与阅读组件、状态展示
    api/                       # HTTP 接口、身份、业务编排
    worker/                    # 解析、索引、导出、来源检查等任务入口
  modules/
    identity/                  # 用户与私有空间
    library/                   # 课程、资源、原件、来源定位
    content/                   # 块、修订、类型校验、锚点
    composition/               # 文档/单元/路线结构、依赖与发布
    reading/                   # 个人插入层、块间位置与融合阅读快照
    connections/               # 语义关系、反向链接与猜想审查
    learning/                  # 任务、会话、尝试、证据、验收
    planning/                  # 预算、诊断、推荐与计划版本
    search/                    # 关键词检索、版本过滤、派生片段
    portability/               # 内容包、迁移、备份与恢复
  contracts/                   # API / JSON Schema / 包格式契约
  adapters/
    storage/                   # filesystem 与 S3 接口实现
    parsers/                   # PDF、Notebook、源码等解析器
    ai/                        # 可选模型调用接口
  migrations/                  # 数据库与内容格式迁移
  deploy/                      # Compose、代理、示例配置与健康检查
  tests/                       # 关键约束、流程和恢复验证
  docs/                        # 架构、操作说明与变更记录
```

模块划分是代码职责边界，不等于创建八个网络服务。前端通过接口读写数据，不绕过 API 直接访问数据库、服务器目录或对象存储的永久凭证。

`contracts` 是内容格式的统一定义；API、Worker、导入器和导出器使用相同版本。块渲染器与解析器分开，升级解析方式不需要改写已有知识。领域内容通过包导入，不新增一套深度学习专属数据库和页面流程。

首版使用 PostgreSQL 的关系表与双向索引查询，暂不部署常驻 Neo4j。依据见[数据库选型实验审阅与首版决策](数据库选型实验审阅与首版决策.md)：当前候选规模下 PostgreSQL 查询已有余量，尚无证据支持承担第二套常驻数据库及同步的维护成本。未来按[数据库对比验证方案](PostgreSQL与Neo4j对比验证方案.md)重评。前端的正文、块引用与关系面板共享同一身份/版本契约；图形展示是这些数据的视图，不是另外的存储来源。

## 3. 运行文件与持久化目录

```text
/srv/learning/
  config/                      # 非敏感运行配置
  secrets/                     # 数据库与外部服务凭证，限制读取
  data/
    postgres/                  # 数据库持久卷，由数据库管理
    assets/sha256/              # 原件与用户附件，内容寻址、不可变
    derived/                   # 预览、OCR 中间件、大型派生结果
    staging/                   # 未完成上传、导入暂存与导出工作区
  backup-staging/              # 备份打包临时区，不是唯一备份地点
  logs/                        # 运行日志，设置滚动与保留期限
```

此路径为部署示例，不要求用户服务器恰好使用 `/srv`。程序镜像不包含 `data`；镜像更新不删除卷；原件不进入 Git。生产部署中的资产键不包含 `<workspace>` 等客户端绝对路径。

文件后端以内容哈希存储字节，显示文件名、扩展名、来源目录和 MIME 保存在数据库。下载时恢复合适的文件名。对象存储后端沿用逻辑分区与资产 ID，业务数据不因后端变化而重建。

服务器端内容编辑写入数据库，标准块 JSON 主要用于交换与导出。源代码、部署配置、业务数据库、文件资产和缓存有不同的生命周期；备份和清理规则分别制定。

## 4. 数据库与任务处理

PostgreSQL 保存结构化内容、引用、工作流、个人学习事实和任务状态。块修订单独一行；组合节点通过有序关系维护；全书正文不保存成一个巨大可变字段。JSONB 适合类型化正文，但仍需固定结构、校验和合适的关系约束。[PostgreSQL JSON 类型文档](https://www.postgresql.org/docs/current/datatype-json.html)

### 任务队列的首版方案

使用数据库 outbox 和 job 表：业务事务提交的同时记录待处理事件；Worker 原子领取任务并取得有期限的租约。租约到期可重新领取，操作本身须幂等。

任务记录：类型、输入修订 ID、配置/处理器版本、幂等键、状态、尝试次数、租约、进度、错误类型、输出摘要与取消状态。长任务分文件/页/批次检查点，不能把整个 2.44 GB 资料库当作一个不可恢复请求。

状态可采用：`queued → running → succeeded`，以及 `retry_wait / failed / cancelled`。取消任务停止后续处理，不删除已经登记的原件或已发布内容。

优先级：用户保存与读取不进慢任务队列；当前材料预览优先于全库抽取；全库 OCR、来源检查和索引重建可限流。首版重计算任务默认低并发，以实测 CPU、内存和磁盘峰值调节。

### 失败恢复

- Worker 退出：租约到期重试，幂等键阻止重复副作用。
- 数据库不可用：API 明确返回未保存；不能显示成功后仅在内存中排队。
- 原件写入成功、业务提交失败：延迟对账，保留临时资产等待重试或回收。
- 解析失败：原件仍可阅读下载，内容状态明确为未抽取或失败。
- 发布成功、索引失败：已发布正文可用，索引状态显示未就绪；不将旧片段标作新版。
- 外部链接失败：记录检查时间和访问状态，本地已有原件仍可用。

## 5. 阅读、编辑与跨设备访问

服务器是在线记录的统一来源。第二台设备登录同一实例即可看到服务端已保存内容，不再增加文件夹同步工具来同时改数据库和原件。

块编辑使用基础修订和乐观并发检查。自动保存可以防抖合并短时间输入，但服务端确认后才能显示“已保存”；保存记录对应一个确定草稿修订。正文历史可区分编辑草稿与正式发布，阅读者默认看到所选发布版。

融合阅读以所选原文发布版叠加当前已保存的个人层。插入/移动请求携带基础个人层修订，服务端事务提交块引用、位置和新视图版本。保存个人笔记推进自己的工作头；不要求重发整份原文，也不修改已固定的其它学习快照。

两设备同时在同一位置操作时，第二次提交返回冲突并保留编辑缓冲；客户端展示最新顺序后再提交。服务器返回融合视图时按权限解析原文、个人块及关系，反向链接和关系计数也不能泄露不在当前范围内的数据。

短暂断网时保留当前页面编辑缓冲并提示未保存；重连后以基础修订重试，冲突时明确处理。首版不承诺关闭浏览器后恢复未提交缓冲，也不承诺离线多设备自动合并。

PDF 通过资产 ID 读取，服务端或对象存储访问层支持浏览器所需的范围读取，避免每次翻页都拉取整份大文件。定位依据资源版本与选择器，不能把临时签名 URL 作为永久书签。

Notebook 和代码先提供静态阅读与原件下载。学习实验在用户选定的外部环境运行，产物再关联回来。未来自动测评需要单独隔离的执行环境；不把“查看课件”变成服务器执行课件。

浏览器存储仅作缓存和偏好；官方文档说明其配额与逐出策略受浏览器管理，因此原件和唯一学习记录保存在服务器并独立备份。[MDN 存储配额与逐出说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 6. 私有访问与文件边界

私有部署仍需身份验证。默认关闭公开注册，初始化一个所有者账号；通过 HTTPS 登录。正式内容、个人记录、原件、派生预览、搜索和导出都执行同一归属权限检查，不能只保护首页。

数据库端口与存储管理接口保持在内部网络。文件目录不作为公开静态目录直接暴露；S3 桶默认私有。通过已鉴权的下载接口或有期限的访问链接获取资产，日志不记录完整敏感令牌。

Cookie 会话采用安全属性及对应 CSRF 防护；导入的 Markdown、HTML、Notebook 输出和 SVG 等不被直接赋予脚本执行能力。解析进程使用有限权限、资源与时间上限，读取不可信文件时不继承生产密钥的全部访问能力。

服务端获取用户提供的资料链接时，需防止访问内部管理地址；导入归档拒绝路径穿越与越界符号链接。这些是服务器导入功能的实现边界，不增加用户日常阅读步骤。

模板包导出默认排除个人笔记、学习记录和密钥。当前高校资料转入服务器后默认私有；对外分享包按已有许可选择包含原件或只保留来源链接，不默认公开整库。

AI 凭证由服务端安全配置，浏览器不携带长期密钥。远程模型调用只接收用户选择范围；未配置 AI 时所有基础学习流程照常运行。

## 7. 备份：数据库、清单和原件一起可恢复

必要恢复数据包括：数据库一致性快照、该快照引用的所有权威资产、资产校验清单、应用/模式版本、部署所需的非敏感配置与恢复说明。数据库角色和权限的重建信息也需保存；密钥用独立受保护方式保管。

v0.3 的备份闭包增加个人插入层、Placement、GapAnchor、融合阅读修订、Relation 修订、EpistemicReview 和位置迁移决定；它们是权威记录，不能当作页面布局缓存清掉。关系端点、个人图片与固定视图涉及的旧版本同样进入引用保护范围。

`pg_dump` 可生成数据库的一致性快照，但不会自动覆盖文件存储，也不包含所有集群级角色信息。因此整个系统的备份需要额外协调资产和角色重建。[PostgreSQL SQL Dump 文档](https://www.postgresql.org/docs/current/backup-dump.html)

### 首版的一致性步骤

1. 创建备份作业，进入短暂业务写入维护窗；暂停新发布、笔记保存、上传定稿与 Worker 业务写入，等待在途事务收束。阅读可继续，客户端明确显示暂不能保存。
2. 在业务状态稳定时生成数据库一致性备份及匹配的资产 manifest，记录备份 ID、模式版本和所需资产集合。备份控制状态单独处理，不混入需要一致的学习数据。
3. 为清单内资产建立保留保护，防止复制完成前被清理。确认清单和数据库快照完成后可恢复业务写入；不可变资产允许随后继续复制。
4. 按 SHA-256 复用已有备份资产，只传新字节；每个备份都有**完整所需资产清单**，不是只有增量日志。派生缓存可以不备份，已人工校正或承载锚点的权威快照必须备份。
5. 校验文件大小、摘要及数量，将必要内容传到不同故障域，例如另一台主机或独立对象存储。
6. 所有必要对象可读取且校验通过后，才把该备份标为 `complete`；中途失败保持不完整状态并保留上次有效备份。

小规模个人实例优先采用清晰可验证的维护窗协议。未来需要持续无感备份时，再实现一致快照协调或数据库连续归档，不能把“直接复制正在写入的数据目录”当作同等保证。

增量备份去重与备份过期清理必须联合计算：只要任意保留备份清单仍引用一个资产，就不能清掉共享字节。备份端保护与生产端未引用文件清理是两套范围。

### 建议的运行目标

初期可配置每日备份和升级前备份；恢复点目标暂定不超过 24 小时的数据损失窗口。这个目标以最近一次**成功且可核验**的备份时间衡量，任务按时启动不代表达标。更短窗口需提高频率或增加数据库归档。

建议保留最近 7 个日备份和 4 个周备份，具体按空间与使用情况调整。这是未来配置建议，本次没有创建定时任务。恢复时间目标先通过演练实测，再给出承诺；不按文件大小推测已经具备某个恢复时限。

## 8. 恢复与演练

恢复到一个新实例，避免直接覆盖唯一可用服务：

1. 验证备份状态、清单和摘要，确认应用版本、数据库兼容性与所需密钥可取得。
2. 建立干净数据库和所需角色，恢复内容与学习记录；恢复过程中遇到错误即停止，不能将部分恢复实例标记为可用。
3. 恢复 manifest 要求的资产；新存储位置由 Asset 的存储映射适配，不改块和笔记身份。
4. 校验所有权威引用存在，抽查或全量核验原件摘要。首版现有规模应做全量资产校验。
5. 重置已失效的 Worker 租约，将可重试任务重新排队；外部副作用任务依据幂等记录核对，不能盲目重新发送。
6. 重建预览与检索，索引未完成期间仍可按目录读取权威内容。
7. 验证登录、旧发布版、块历史、原件定位、私有笔记、任务与验收；确认无误后再切换用户访问。

恢复演练至少包含一条完整链路：某次学习实例 → 固定路线 → 单元 → 内容块修订 → 原件位置 → 笔记 → 实验产物 → 验收规则。另检查一份已升级组合和它的历史版本，以证明备份保留了版本关系。

还要恢复一份融合阅读视图：核对个人笔记/图片在正确间隙、猜想及支持/反对关系指向正确修订、待放置内容和旧位置记录仍可找回。只校验正文数量无法证明插入层和关系恢复完整。

记录恢复用时、缺失对象、数据数量差异与人工步骤。初次上线前演练一次；重要模式迁移或存储迁移后再演练。只有成功生成备份文件，不能宣称已验证可恢复。

## 9. 发布应用与升级模式

应用发布与学习内容发布是两个流程。更新应用镜像不会把内容库恢复成内置演示数据；内容修订也不需要重新构建整个应用。

建议使用固定版本镜像与依赖锁定文件；数据库迁移只由一个受控进程运行。升级前生成恢复点，确认 API 与 Worker 使用兼容模型，再逐步切换。界面、接口、内容包格式和数据库模式的版本分别记录。

Compose 的生产配置应有明确端口、环境设置、持久卷和重启策略，应用代码在镜像内管理；这是单服务器起步形态，后续有实际负载再扩展。[Docker Compose 生产部署说明](https://docs.docker.com/compose/how-tos/production/)

尽可能先做向后兼容的字段扩展与回填，再收缩旧结构。数据库模式发生不可逆变化时，不能承诺只退回旧镜像即可回滚；必须使用已验证的恢复路径并说明期间新写入如何保全。

内容块 `schema_version` 的升级不得静默覆盖旧修订：保留旧修订可读能力，或通过有记录的转换生成新修订。纯存储布局迁移也应核验语义未改变，必要时保留原序列化表示供核对。

## 10. 搜索、规模与容量

首版先做标题、标签、课程/类型/版本筛选，以及经验证的正文关键词检索。中文分词或子串召回要用真实中文问题和资料评估；不能把默认英文检索配置当作已解决中文搜索。向量检索之后再接，仍以块修订和原件定位为来源。

搜索只覆盖有权限、属于所选发布快照的内容。原件抽取中的草稿和已精编知识分开呈现；尚未完成 OCR 的扫描件显示“正文未索引”。禁止用全文已搜索的表象隐藏缺失覆盖。

现有 323 份原件合计约 2.44 GB；这是已知输入大小，不是服务器总空间要求。存储预算应包含：

```text
实际所需空间 = 所有保留原件版本 + 数据库及历史
             + 预览/OCR/索引 + 临时上传/导出峰值
             + 本机备份暂存 + 运行余量

异机备份空间另算；同一大文件出现新版本时可能增加完整文件体积。
```

不根据“单人”直接承诺极小内存即可承受所有 PDF/OCR 任务。部署选型前用真实样本测量：大 PDF 阅读、文本 PDF 抽取、扫描件 OCR、Notebook 预览、块查询、索引和备份峰值，再决定 CPU、内存、磁盘与并发。应用服务器首版无需承担大模型训练，本地模型推理属于另一个可选服务。

出现以下实际问题再扩展：大批解析拖慢阅读时将 Worker 放到另一台主机；资产持续增长时切对象存储；关键词检索成为瓶颈时独立检索组件。每一步保留内容 ID、修订和业务接口。

## 11. 从当前目录迁移到服务器

迁移按可重复批次完成，原 Windows 文件保留为迁移来源与回退副本。

| 当前文件 | 进入系统的位置 | 保留关系 |
|---|---|---|
| `深度学习与大模型工程手册.html` | 原稿归档 + 标准块 + 章节组合 | s 编号/锚点映射与原始正文对照 |
| `顶尖高校深度学习课程指南.html` | 阅读归档 + 课程/来源/路线组合 | c/r 等旧锚点映射 |
| `.courses-build/courses.json` | 课程与学期元数据 | 原 ID、来源地址、版本说明 |
| `课程课件/资料清单.json` | Resource / ResourceVersion / Asset 清单 | 本地路径、源 URL、SHA-256、格式和页数 |
| `课程课件/` 原文件 | 文件存储原件区 | 字节校验、下载名与来源 |

| 现有静态 Notebook/源码阅读副本 | 可保留旧阅读归档，后续按需重建 | 不替代原代码或 Notebook |

Python 路线文件由受控迁移器读取其已知数据结构或先导出 JSON；未来上传者提供的任意 Python 文件不会因此获得执行权。

迁移批次记录条数、字节、哈希、来源映射、失败列表和已导入状态。目标数据库中先暂存验证，整批通过后对用户可见。重跑相同批次复用相同记录；来源更新另开版本批次。

验收基线为 21 个课程条目、349 条资料索引、323 份本地原件、11 阶段和 48 学习周。原件与在线入口两类都要保留访问状态；不能为了凑齐本地数量而生成虚假的空文件。

首批手工抽查选 PDF、PY、Notebook 各一类，并检查旧链接、新资产路由、源站入口和块级定位。新学习记录只来自之后的真实使用或有依据的历史成果导入，不从文件存在推断学习进度。

## 12. 上线前检查与日常可观测性

| 范围 | 上线前验收 | 日常检查 |
|---|---|---|
| 服务与权限 | 两台设备可登录；未登录不能取得私有内容和文件 | 请求错误、身份失败、异常访问 |
| 数据持久化 | 重建 API/Worker 容器后数据与原件完整 | 数据库连接、磁盘余量、保存失败 |
| 块与发布 | 原子发布、冲突、版本回看、回滚正确 | 失败发布、悬空引用、待处理迁移 |
| 后台任务 | 中断可重试，重复任务结果等价 | 队列积压、租约超时、解析失败 |
| 学习流程 | 阅读→笔记→尝试→证据→验收可走通 | 用户未保存提示、任务阻塞原因 |
| 备份恢复 | 干净实例恢复并核对完整链路 | 最近有效恢复点、校验失败、异机副本状态 |
| 检索与来源 | 版本过滤正确，抽取覆盖可见 | 索引滞后、原链接失效、待复核候选 |

应用运行日志保存必要的请求/作业关联 ID，不默认写入完整私人笔记、模型输入或密钥。备份失败、空间不足、持续处理失败属于应提示用户的可行动事件；通知渠道在实际部署时配置。

第一版的实施纵向范围是：完成私有服务启动，登记一个原件，维护几个块并组合为两份文档，在融合阅读中插入笔记、图片和猜想，建立一条明确的证据关系，完成一次学习与批注，再演练内容升级、位置迁移及全量恢复。满足后再批量导入现有课程库。

本文不设未经测量的性能或恢复时间保证；域名、宿主机配置、存储后端和备份目标是部署参数。架构支持以后迁移这些参数，稳定的内容与学习记录身份保持不变。
