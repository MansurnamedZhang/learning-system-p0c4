# PostgreSQL 与 Neo4j 对比验证方案

2026-09-17 · 验证设计 v1 · 保留测前合同

实施状态：用户指定的「本地 Linux 服务器」任务已执行隔离查询实验。来源任务已复核正确性记录和 33,600 条正式测量，选型建议见[实验审阅与首版决策](数据库选型实验审阅与首版决策.md)，阶段证据见服务器测试协作记录（私有或未公开参考）。下文保留实施前锁定的合同；其中“本次尚未执行”等语句描述制定方案时的状态，当前结果以审阅文档为准。

关联：[系统总体设计](学习系统设计方案.md)、[连续阅读与思考块](连续阅读与思考块设计.md)、[存储规范](内容分块与存储规范.md)。

## 1. 这次实验要决定什么

决定首版是否需要常驻 Neo4j，以及它能否作为 PostgreSQL 权威数据的可重建关系查询层。先验证真实学习业务中的查询与维护要求，再决定数据库组合。

验证范围包括：固定版本的块与关系、证据来源、关系撤回、原文引用、个人插入位置、影响范围、图同步与恢复。不需要先做完整编辑器、运行大模型实验或导入全部 2.44 GB 课件。

使用现有“大模型工程手册”的 RAG 和 Attention 主题作为业务背景。数据库用例中的观察与支持/反对关系是**明确标注的测试夹具**，用于检查软件行为，不代表已经完成真实科学实验，也不验证猜想本身的真假。

最终输出应包含：可重复的数据包、同义 SQL/Cypher 查询、预期答案、正确性结果、性能原始记录、维护演练记录，以及采纳/延后/继续验证的决定。当前交付的是本方案，尚未创建这些运行结果。

## 2. 先比较两种查询实现，再验证混合架构

| 实验阶段 | PostgreSQL 侧 | Neo4j 侧 | 目的 |
|---|---|---|---|
| 查询正确性 | 从共同数据包导入，查询关系表 | 从同一数据包导入，查询属性图 | 检查是否表达同一业务语义 |
| 查询与维护成本 | 索引、SQL、递归查询、维护脚本 | 约束、Cypher、关系节点、维护脚本 | 比较查询表达、耗时和变更代价 |
| 混合运行 | 权威写入 + 同事务 outbox | 消费事件形成可重建图 | 验证实际引入第二个数据库的代价 |

前两阶段不以同步延迟干扰纯查询比较。第三阶段必须测试整个 PostgreSQL + Worker + Neo4j 组合；不能只用 Neo4j 单次查询更快，就推断整体产品更合适。

两边保留相同业务对象：Block、BlockRevision、RelationRevision、来源运行、组合版本、Occurrence、个人层和学习实例。复杂关系有独立身份，不能在 Neo4j 中删去版本、条件和审查字段来获得一个更简单但含义不同的图。

PostgreSQL 为端点、关系类型、空间、快照等查询维度配置适当索引；Neo4j 为应用 ID 设置可用的唯一性约束/索引。双方都获得一次同等范围的查询计划检查和调优机会。

Neo4j 中有独立属性和批注的关系可投影为 RelationRevision 节点，再连 FROM/TO 两个端点。一次“业务关系跳转”可能对应两条物理边；深度和结果必须按业务关系计算，不能把数据库物理跳数直接拿来比较。

## 3. 场景 A：猜想—证据—反例—结论

背景问题：检索片段附加符号定义，是否能减少回答中的符号含义错误？

`H@1` 表示 H 的第一版，`H@2` 表示范围更明确的第二版。所有测试项带固定空间、快照、版本和可见性。下面的关系与观察均为测试数据。

| 对象 | 设定 | 用于验证 |
|---|---|---|
| H@1 | 较宽泛的猜想 | 旧命题仍可复现 |
| H@2 | 限定任务和测试条件的新版猜想 | 新版不继承旧支持关系 |
| E1@1 | 来自运行 RUN1，支持 H@1 | 正常支持关系 |
| E2@1 | 也来自 RUN1，支持 H@1 | 两个证据块可能来自同次运行 |
| X1@1 | 来自 RUN2，反对 H@1 | 支持与反对同时存在 |
| E3@1 | 来自 RUN3，支持 H@2 | 新版的明确支持关系 |
| E4@1 | 仅 related_to H@1 | 相关不等于支持 |
| E5@1 | 对 H@1 的支持关系已撤回 | 不应出现在当前有效证据中 |
| C@1 | 使用 H@1、E1@1、E2@1、X1@1 形成条件化结论 | 结论依据可追踪且固定版本 |
| EH@1 | 属于另一个不可见空间，关联 H@1 的干扰数据 | 数据和计数均不泄露 |

为 C@1 显式保存 `basis_refs`，说明它实际采用哪些块/关系修订。不能根据页面邻近或看起来相关，自动推断它使用过哪些证据。

### 预先锁定的查询合同

| 编号 | 问题 | 预期答案 |
|---|---|---|
| A1 | H@1 当前有哪些有效支持和反对？ | 支持 `{E1@1,E2@1}`；反对 `{X1@1}`；E4/E5/EH 均不进入 |
| A2 | 这些证据来自哪些运行？ | RUN1 → E1/E2；RUN2 → X1；共 2 个来源运行组，支持侧只有 1 组 |
| A3 | H@2 当前有哪些有效支持？ | 仅 `{E3@1}`；E1/E2 只可出现在明确标为旧版关系的单独结果中 |
| A4 | C@1 当时采用哪些判断与证据？ | 恰为其固定 basis_refs，不因 H@2 或 E3 新增而变化 |
| A5 | 撤回 E1 的支持关系后，H@1 的当前支持是什么？ | 只剩 E2；旧快照仍可看到撤回前的 E1/E2 |
| A6 | 用受限身份执行以上查询 | EH 的正文、标题、关系和计数均不返回；关系不能借不可见中间节点传播 |

“运行组数”仅表示来源去重，不是统计独立性证明。即使 RUN1 与 RUN2 不同，也不能由数据库关系直接证明实验彼此独立。

A5 等变更用例从固定基线单独重置执行，或显式指定前后快照；不能让用例执行顺序偷偷改变其他预期答案。

## 4. 场景 B：知识修订—影响范围

背景：修订 Attention 工程说明中的一个知识块 K。K@1 为旧说明，K@2 为修订说明；此处检验版本关系，不在测试夹具中宣称具体 API 语义正确。

建立如下**消费者 → 所依赖版本**的关系，反向遍历得到影响范围：

```text
Dtrain@1 ─引用────→ K@1
Dref@1   ─引用────→ K@1
U@1      ─需要上下文→ K@1
R@1      ─包含────→ U@1
L1       ─固定路线→ R@1
N@1      ─批注────→ K@1，位置绑定 Dtrain@1 的 occurrence
Dother@1 ─相关────→ K@1

修订操作：创建 K@2，只将训练文档升级为 Dtrain@2 → K@2。
```

另保存一条已完成验收 A0，其任务和规则仍固定旧版。N@1 的文字与批注位置是独立数据。Dtrain@1 中再增加第二次 K@1 出现，用 occurrence ID 区分，N@1 只关联第一处。

查询先声明传播规则：`引用 / requires_context / 包含` 属于确定内容依赖；学习实例的固定路线作为受影响实例单独列出；批注属于人工复查候选；`related_to` 不传播必需更新。影响范围不等于所有命中对象都必须自动升级。

| 编号 | 问题 | 预期答案 |
|---|---|---|
| B1 | K@1 修订时哪些内容是直接消费者？ | `{Dtrain@1,Dref@1,U@1}`，按对象去重；另返回具体 occurrence，不丢重复出现位置 |
| B2 | 哪些内容在传递依赖范围内？ | `{Dtrain@1,Dref@1,U@1,R@1}`；同时提供合法依赖路径作为解释 |
| B3 | 哪些学习记录需要提示？ | L1 列为所固定路线受影响；N@1 列为批注复查候选；A0 保留原验收事实 |
| B4 | Dother@1 是否进入必需更新范围？ | 否；允许在单独的“相关内容”列表展示 |
| B5 | 只发布 Dtrain@2 后，现行文档视图引用谁？ | Dtrain@2 → K@2；Dref@1 → K@1；U@1/R@1/L1 维持原版 |
| B6 | N@1 是否同时出现在 K 的两处 occurrence？ | 否，只落在原选中位置；第二处不能自动复制批注 |
| B7 | 新版删除/拆分该 occurrence 后如何处理？ | 原快照与原位置仍可读；新位置确定时记录迁移，不确定时进入待重新放置 |
| B8 | 原文内容回滚后学习事实是否丢失？ | A0、N@1 和期间真实学习记录均保留；只改变当前内容/视图选择 |

再添加两个边界用例：普通相关关系成环时查询有界；试图形成硬先修或组合包含环时拒绝相应变更。必须区分允许成环的知识关系与不允许成环的结构依赖。

## 5. 数据包、正确答案与结果比较

建议的实验目录只描述未来产物，本次尚未生成执行脚本：

```text
experiments/graph-evaluation/
  README.md                     # 版本、环境和重跑步骤
  fixtures/
    base.json                   # 共同逻辑对象与关系
    snapshots.json              # 当前/历史的明确成员集合
    mutations.json              # 修订、撤回、移动、拆分等独立用例
    expected.json               # 手工审定的小样预期结果
  adapters/
    postgres/                   # 表、索引、导入与查询
    neo4j/                      # 投影、约束、导入与查询
  checks/                       # 通用结果规范化、断言和独立基准遍历
  results/<run-id>/              # 原始结果、查询计划、延迟和资源记录
  decision.md                   # 结论、限制和后续条件
```

所有数据使用应用层稳定 ID。每份查询结果返回对象/修订 ID、关系类型、状态、来源组和必要解释路径，不能只比较标题或记录数量。

正确性比较分三层：

1. **独立手工答案：**上面 A/B 的小样答案先写好并冻结。两数据库都必须符合；仅二者彼此相等仍可能共同出错。
2. **结果规范化：**集合按稳定键比较；有阅读顺序的结果按 occurrence/placement 顺序比较；检查版本和来源分组。路径有多个合法答案时校验端点、边类型、权限、深度及连通性，不要求碰巧选择同一条路径。
3. **扩展数据基准：**用独立的简单遍历程序作为参考，配合撤回、版本切换、同源重复和可见性变更等性质检查。参考程序不照抄某一数据库查询的算法结构。

路径查询要声明最大**业务关系**深度、结果上限和排序方式。超出预算返回明确 `truncated/timeout` 状态；不能把被截断的结果标为完整影响范围。语义关系沿路径可达只表示有关联，不自动推导“支持具有传递性”或“猜想已被证明”。

先让全部正确性用例通过，再进入性能比较。任何版本串用、权限泄露、旧笔记丢失或假完整结果，都是阻止采纳的问题。

## 6. 如何公平比较查询表达与性能

### 数据规模

| 档位 | 规模定义 | 目的 |
|---|---|---|
| 小样 | 场景 A/B 中逐条登记的对象与关系 | 人能审查所有答案 |
| 中样 | 10,000 个块修订、50,000 条逻辑关系修订 | 观察长期个人知识库的候选量级 |
| 大样 | 100,000 个块修订、500,000 条逻辑关系修订，按设备能力选做 | 观察扩展趋势，不直接作为首版需求 |

上述数值是待测试档位，不是对用户未来资料规模的预测。物理节点/边/行数、资产字节和索引大小另外报告，不能假定两引擎物理规模相同。

扩展数据保留多个版本、跨文档复用、高度连接的热点、相关关系环和局部小群体，并使用固定种子。不能只复制互不相连的小样，因为那不能代表复杂关系查询。

### 统一运行条件

- 固定数据库版本/镜像摘要、驱动、操作系统、CPU、内存总限额和磁盘环境。Neo4j 所用版本/版本类型在报告中明示。
- 在同一环境分轮运行两引擎的单库测试，避免同时争抢资源；索引就绪后更新必要统计信息。
- 输入相同的逻辑数据、查询参数、快照、权限、深度与输出范围；双方返回完整等价数据，而非一方只计数另一方取全文。
- 默认并发 1，补充并发 4 的轻负载测试。批量导入与重建性能单独测量。
- 每组先预热 20 次，再用固定但有变化的参数集测量至少 100 次，独立重复 3 轮，交替运行顺序。样本量与原始记录保留，结果不只取最好的一次。
- 区分稳定热缓存和启动后首次访问。单纯重启进程不等于清空操作系统缓存；未受控的情况不得标为真正冷缓存。
- 分别记录数据库执行时间、驱动往返及完整结果读取时间、接回 PostgreSQL 正文后的端到端时间。

### 记录内容

| 维度 | 测什么 |
|---|---|
| 正确性 | 精确答案、版本、范围、撤回、权限和定位 |
| 延迟 | 各查询 p50/p95、波动、超时率、结果条数 |
| 资源 | 空闲/运行内存、CPU、磁盘、索引大小；混合方案统计所有组件合计 |
| 写入与重建 | 导入、单块修订、关系撤回、全量建图耗时与失败恢复 |
| 查询表达 | 业务规则是否直接可见、额外视图/预计算/过程数量、调试步骤 |
| 改需求成本 | 修改查询/模型/同步器的实际步骤、耗时、缺陷及补充验证 |

PostgreSQL 使用 `EXPLAIN (ANALYZE, BUFFERS)` 辅助理解实际执行；Neo4j 使用 `EXPLAIN/PROFILE` 检查计划和执行。带实际执行的计划采样放在正式计时外，避免把诊断开销混进常规延迟。两者的内部 cost、DB Hits 或 buffer 数值不属于相同计量单位，不能直接按数字高低排名。[PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)、[Neo4j 查询计划](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/)

SQL 与 Cypher 的行数可记录，但不作为主要评分。一个少写十行却漏掉版本过滤的查询没有优势。维护耗时同时记录实现者熟悉程度和顺序，避免把学习新语言的时间全算成数据库缺点。

## 7. 必须亲自演练的维护与同步情况

先对两种实现执行相同需求变更：增加一种关系类型、给关系加审查条件、查询旧快照、撤回一条关系、将一个块拆分、修改可见范围。记录数据迁移、代码位置、回归用例和恢复步骤。

如果 Neo4j 的查询价值成立，再测试 PostgreSQL 权威写入 + outbox + Neo4j 投影：

| 故障/变化 | 通过条件 |
|---|---|
| Neo4j 停止，继续编辑块和笔记 | 权威保存和基础阅读正常；图功能显示不可用/同步中，或回退到正确的 SQL |
| 同一事件重复投递 | 节点/关系不重复，结果与投递一次相同 |
| 新旧事件乱序到达 | 旧事件不回退当前修订，不复活已撤回关系 |
| 更新关系成功但 Worker 尚未确认即退出 | 重启后重试得到等价结果，不丢事件 |
| 两端版本尚未全部建图 | 不把不完整发布批次标为可查询完成 |
| 可见范围撤销但图尚未同步 | 权限检查仍基于权威当前范围，内容、路径与计数不泄露 |
| 请求固定旧学习快照 | 只沿快照允许的块/关系版本查询；不能混入最新证据 |
| 删除可重建图，再从源数据恢复 | 所选快照下的节点、关系和 A/B 答案一致 |

同步进度必须确认事件缺口和批次完整性，不能将见到的最大事件 ID 当作此前全部处理完成。应用可带上所需发布批次/视图版本请求查询，图未就绪就明确等待或回退，不返回冒充最新结果的旧图。

建议在小负载下试行“图更新 p95 不超过 2 秒”的候选目标，同时测量批量重建期间的延迟；这是产品讨论用目标，不是 Neo4j 能力承诺。实际要求取决于用户是否必须在刚保存后立即看到完整反向关系。

混合方案的备份以 PostgreSQL、原件及权威记录为核心，另保存图投影器版本和配置。Neo4j 备份可缩短恢复时间，但仍需演练从权威数据重建。恢复不能只统计节点数，还要验证版本、撤回状态与关键路径。

## 8. 决策规则要在测量前写定

先采用以下候选交互目标，实施前可以调整，但不要看完结果再为喜欢的方案改门槛：

- 中样并发 1：局部关系和反向链接端到端 p95 ≤ 250 ms。
- 中样并发 1：声明范围内的影响分析端到端 p95 ≤ 1 s。
- 版本、权限、历史复现、撤回与恢复的正确性用例全部通过。
- 额外资源必须适合实际部署机器；有明确重建、升级和排错流程。

| 测量结果 | 首版决定 |
|---|---|
| PostgreSQL 已达到目标，关系查询维护清楚，Neo4j 收益有限 | 首版用 PostgreSQL，保留图接口与数据契约 |
| 高频多层查询在合理调优后仍未达标，Neo4j 达标，且同步/恢复通过 | 纳入 Neo4j 查询层 |
| 两者都达标，Neo4j 在多次真实需求变更中明显简化维护 | 将收益与额外服务、同步和排错成本一起评审，再决定常驻 |
| Neo4j 单次更快，但历史版本或同步正确性不过关 | 暂缓采纳，先修复模型与一致性 |
| 只有超出首版需求的大样出现明显优势 | 记录扩展条件，不据此强制首版承担额外组件 |

例如 8 ms 对 3 ms 的差异即使倍数明显，也可能不影响用户体验；1.5 s 对 200 ms 则更值得调查。两组数字仅解释决策方法，**不是本项目的测量结果**。

结果表为每个查询记录数据包摘要、参数、期望结果摘要、实际结果摘要、引擎/索引配置、样本数、延迟、资源、失败和限制。所有未执行项标“未运行”，不填推测值。
