## 能力与持有关系

现有非测试库接口 `prepare_source_backup`、`finish_source_backup`、`abandon_source_backup` 使用精确绑定的源端能力。源数据库名称、OID 和 system identifier 只是一部分身份：物理克隆可以具有相同的三个值，因此还要检查实际执行器的命名空间、源容器与 postmaster 身份、Unix socket，以及原准入连接持有的两个随机会话锁。

第一次可能改变状态的动作之前，必须完成原连接与源端的绑定。创建保护记录、写源日志、变更 CONNECT、生成 dump 和发布本地 pin 都受此顺序约束。所有 native 子进程共用同一个被准入的源连接，不重新从池中借一条连接充当见证。

子进程监督器持有源连接、随机锁、注册表租约、已登记目录句柄、私有隔离证明和已创建的捕获保护。取消、超时、输出超限和子进程失败时，先终止并等待子进程回收，再结束这些对象的持有。恢复 CONNECT 前后均重新检查绑定；无法确认的状态保留关闭或隔离语义。

固定 native 工具为 PG18.6 的 `/usr/lib/postgresql/18/bin/psql` 和 `/usr/lib/postgresql/18/bin/pg_dump`，连接 `/var/run/postgresql` 中的本地 socket、端口 5432、固定管理角色与准入数据库。dump 为 custom 格式，上限 1 GiB，绝对期限 900 秒，64 KiB 流块；这些是显式容量上限，不是已经测得的性能。

## 安装与执行前提

本阶段交付库接口和已安装管理端观察生产器 `scripts/p0c4_source_isolation.py::observe_source_endpoint`。应用使用这些现有接口；本阶段没有增加一个通用管理服务。

1. 使用实际当前源码包的构建身份编译应用，独立签发原始 source-control binding，并保留应用 ELF 的哈希。注册表、源控制、本地 pin、原件及 staging 目录先由管理端独立登记。
2. 源 PG 使用固定 PG18.6 镜像。四个 volume 挂载点为 `/var/lib/postgresql`、`/var/lib/knowweave-source`、只读 `/target`、`/var/lib/knowweave-c4/registry`；三个只读文件挂载点为 initdb 脚本、postgres 密码和 admin 密码。总计七个挂载，无 healthcheck，单独的内部网络，没有公开数据库端口。
3. 管理控制端持有私有证明目录与隔离锁，对精确的容器、project 和当前 epoch 调用非测试观察生产器。应用 ELF 位于只读 `/target`，镜像内须具有兼容运行库与固定 PG 客户端。数据库凭据由受控私有文件或管理连接配置读取。
4. 应用通过已有的精确容器 `docker exec --user 0:0` 执行器运行在源 PG 内，使用清理后的环境调用库接口。源 PG 内没有 Docker CLI 或 socket。独立证明与注册表由库重新验证，不能由调用者提供一个布尔值代替。
5. 控制端负责对精确 PG 容器执行停止和独立读回；native 子进程退出并不能证明 PG 已停止。

原有独立 manager 容器不在该 PG 命名空间内，其新捕获请求会在状态变更前被拒绝。普通绑定验收中的只读拒绝、关闭连接与保护原控制日志场景仍采用原有执行角色。具体已安装应用的可执行文件与非敏感输入属于应用自身接口，不是完成计划中的任意命令选择器。

## 固定验收入口

根控制端使用现有入口，读取本轮私有的固定计划：

```text
python3 scripts/p0c4_completion_acceptance.py run --plan PRIVATE_PLAN --case FIXED_CASE
python3 scripts/p0c4_completion_acceptance.py verify --result PRIVATE_RECEIPT
```

每轮先冻结实际 Git 字节、核验源码和工具，再创建新 UUID、项目、目录、卷与未占用子网。计划只允许固定映射和资源预算；复核命令只读。

| 固定 case | 实际测试关注点 |
|---|---|
| `source-clone` | 真正物理复制，三个数据库标识相同，命名空间不同，克隆没有原连接的随机锁；拒绝发生在日志、ACL、dump、pin 和注册表变更之前 |
| `source-bound-dump` | 固定本地 socket 与客户端、原准入 backend、真实输出和成功回收 |
| `source-restart` | 当前测试执行原会话随机锁丢失；证据明确 `actual_postmaster_restart=false` |
| `source-cancel` | 真实 native dump 的超时、取消与输出超限；回收顺序、关闭 CONNECT 和保护记录 |
| `source-dump-failure` | 真实子进程失败后的保护和关闭状态 |
| `source-lifecycle-eight` | 八个固定生命周期用例、首轮文件系统/合同、源码/签发/编译/目录/审计/回收证据 |

只有 `source-clone` 具有两个精确的新 PG。原容器的第八个挂载仅为本轮复制目标卷；正常源端始终采用七挂载协议。这不是恢复目标的出生证明协议。

另行运行原有普通用户入口的 admission-five 和 binding-four，分别记录五项与四项真实结果。绑定入口附带的两项准入回归单独计数。注册表十一项、端点五项和生命周期八项各自具有明确证据范围。

## 故障注入与复核

测试专用超时和超限配置不改变生产上限。暂停 postmaster 由既有控制端对本轮拥有的精确 PG 发送固定 STOP/CONT，双方确认实际暂停和恢复状态、epoch 与原连接挑战。清理过程中先恢复待处理的暂停，再执行精确停止及读回；确认失败时不能产生通过收据。

容器内 PID 1 有特殊信号语义，容器内部 `kill` 返回成功并不足以证明暂停。依据 [Linux PID namespace 手册](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)，测试使用外部控制端，而非增加容器权限或开放调用者选择信号、PID、SQL、命令的接口。

生命周期八项收据复核要求：有效且相等的源码 before/after 哈希；独立 issuer、实际 SQL 身份与原控制绑定；当前编译及两个实际保留可执行文件；完整的 before/after/final 目录和二进制审计。缺失、空对象、矛盾值以及布尔值混作整数会被拒绝。只有既定 `control-held`、`pins-held` 路径变化在 dev/inode 不变时被接受。

已经读回的真实结果只属于其准确源码包和用例，不能替代当前全部 Linux/PG、取消回收与停止读回门。失败取消批次停止并留卷；未产生的审计和回收观察保持缺失。后续记录须来自最终审查后的冻结包及新隔离项目。

独立备份存储尚未配置。设计附录 B1 还明确了首次签发的操作资格：失败或失去原操作后，磁盘上的完成标记不能自行恢复该资格。独立目标接入阶段必须实现并验证真正的跨操作提交准入；仅安装密钥不足以启用当前独立执行器或新建租约的发布入口。已验证签名的历史完整备份仍按目标端证据恢复，不要求原源库在线。当前不声明 `CompleteBackup`、正常恢复或最终 P0-C4 已完成。
