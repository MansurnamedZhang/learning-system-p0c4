# Snapshot directory v1

The first exchange format is an ordinary directory. Compressed archives are not accepted. A package is available only after the private staging directory has been verified and atomically renamed to its ready name. A partial directory is never a delivery result.

`manifest.json` contains either `exact_import_v1` or `reading_copy_v1`. The latter has a new `copy_id` and cannot be imported as an exact snapshot. `files` lists every other file, sorted by path, with its byte length and lowercase SHA-256. `validation.json` is the canonical JSON `{"status":"validated"}`. The manifest excludes itself from `files`; its own SHA-256 identifies the verified bytes and is not an authorization token. For exact packages neither the job ID nor staging name enters this hash; reading copies include their generated copy identity.

Exact object files use `objects/<closed-table>/<typed-primary-key>.json`. Primary-key components are canonical lowercase UUIDs prefixed `u-`, closed reference kinds prefixed `k-`, or canonical nonnegative decimal positions prefixed `p-`, joined with `__` in database primary-key order. The JSON holds one complete `SnapshotRow` and uses `learning_core::canonical_json`; its `sha256` is the hash of the full `immutable_values` record. Original bytes, when requested, use `assets/sha256/<first-two-hex>/<lowercase-sha256>` and must hash to the filename. An exact package can instead set `requires_destination_assets=true` and omit original bytes; the destination then has to verify its own exact authorized assets. A reading copy may include escaped `reading.md` and `reading.html` and generic omitted markers. It carries no exact identity fields.

The package accepts at most 2048 files, including `manifest.json`; each JSON or reading file is at most 8 MiB and their combined bytes at most 64 MiB. Each included original is at most 128 MiB and all included originals at most 512 MiB; a metadata-only package contains no original bytes and does not charge that byte budget. The exact closure also uses 2048 objects, 4096 reference edges, reference depth 32, composition depth 16, 4096 occurrences, and 8 MiB of body text, enforced by the core planner. Unknown entries, noncanonical paths or JSON, links and reparse points, duplicate paths, and manifest/hash mismatches are invalid.

Incoming data enters through caller-opened streams. The package writer never reopens a caller-supplied source path. This version supports authoritative staging, validation, and verified delivery on Linux under an isolated service identity and a service-owned 0700 staging root. It retains directory handles, opens entries relative to them with no-follow semantics, and returns sealed delivery handles. Windows staging entrypoints fail before filesystem side effects; Windows privacy, handle-sharing, and durability guarantees remain to be implemented and accepted separately. Any future external-directory adapter must open every component relative to retained directory handles with no-follow semantics before passing file handles to `stage_incoming`.

## Fenced export jobs

C3 export events use a strict version-1 `snapshot_export` input. Its business key includes actor, space, and the SHA-256 of the canonical complete request, including mode, personal/original options and explicit roots. A request ID cannot be reused with changed options. Identical requests share a business event; enqueue returns its reserved job ID and commits the event and request receipt together. Migration 0014 preserves the C2 asset payload/key and limits `p0c2_claim_job` to asset events. `p0c3_claim_snapshot_job` alone claims export events. Legacy dispatchers can create C3 jobs, but legacy claimers never consume an export attempt. C3 uses `snapshot_queued`, `snapshot_running`, and `snapshot_retry_wait` as its nonterminal database states. The old binary’s fixed C2 status scan cannot see them, so an earlier C3 backlog cannot fill its scan limit. New workers scan up to 64 jobs from each configured family per cycle; C3 renewal/checkpoint/failure/cancellation/success route to separate fenced functions. The public `JobStatus` vocabulary is normalized by the persisted event kind.

The Worker optionally accepts an absolute `SNAPSHOT_ROOT`, provisioned as a private, service-owned 0700 directory outside static/public roots. Without it the Worker continues C2 processing and leaves C3 attempts untouched. Packages live under a generated job UUID directory and a generated lease-token package name. Each attempt is isolated and cannot overwrite another attempt's package. A reading copy uses the stable job ID as its logical copy identity; the lease token selects only the attempt directory, so retrying unchanged content preserves the manifest hash. These internal names are never returned by `SnapshotDelivery`.

An exact export uses the complete authorized immutable closure; `include_personal=false` produces a sanitized reading copy for supported reading projection versions 1 and 2, including readings with saved relation/review selections. Unknown future versions are rejected. The Worker re-plans current content, locks every required grant in UUID order, rechecks under those locks, verifies the staged package and atomically writes the result with the current lease token. A stale token cannot publish. Delivery uses a new transaction, rechecks the same current authorization/content and grant set, then reopens the winning package relative to the private service root using the stored manifest hash. It returns sealed, verified file handles. Revocation taking the grant lock first prevents completion/delivery; revocation arriving after delivery acquired the locks waits until those handles have been obtained. Handles already delivered are not retroactively revocable.

Failed and superseded attempts are retained only under the private job directory. No automatic deletion, public download URL, expiry policy or HTTP endpoint is added by this version. A future collector must reclaim only explicitly selected, inactive job UUID directories; it must never use package paths supplied by a caller.
