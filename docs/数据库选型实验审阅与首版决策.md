# 数据库选型实验审阅与首版决策

2026-09-17 · 本地 Linux 隔离实验已结束 · 来源任务完成归档复核

**总验收状态：NOT_PASSED。** 查询基准完成，补充权限检查存在 4 项已复现、未修复的失败。本文件给出首版技术路线建议，不批准任何实验原型直接上线。

## 1. 首版建议

**首版采用 PostgreSQL 保存权威内容和关系，并执行关系查询；暂不常驻 Neo4j。** 保留独立的关系查询接口、稳定块/关系身份和版本契约，将来有真实瓶颈时再增加可重建图投影。

本次证据支持的是这个系统当前两类业务的实现顺序。它不能证明 PostgreSQL 对所有图查询都更快，也不能证明本次简化程序已经具备生产系统的权限、发布和并发保证。

主要理由：

1. 10,000 个块修订、50,000 条逻辑关系的候选规模下，两库都能表达已测查询。PostgreSQL 的实测延迟已有充分余量。
2. 当前 Cypher 实现保留了关系独立身份、版本、可见范围和审查状态，其维护优势尚未得到多次真实需求变更的证据支持。
3. 引入 Neo4j 还需维护事件投递、图就绪状态、权限撤销和重建；本次最小演练只能验证其中部分机制。

## 2. 实验与复核范围

执行任务为用户指定的「本地 Linux 服务器」。测试使用独立容器、网络和数据卷，无宿主端口；每个数据库限制 2 CPU / 4 GiB。数据库为 PostgreSQL 18.6 和 Neo4j Community 2026.08.1。宿主为 i7-13700F / 30 GiB 内存，既有业务服务仍在运行。

测试内容是明确标记的合成业务数据，不是对 RAG 猜想的科学验证。中样包含 10,000 个块修订、160 个辅助实体和 50,000 条逻辑关系。Neo4j 将关系修订建为独立节点，一次业务跳转对应两条物理边。

来源任务已只读审阅夹具、手工答案、Python 参考、SQL/Cypher、基准脚本和最小 outbox 脚本，并对原始记录另行运行复核脚本（私有或未公开参考）。结果保存在复核结果与文件摘要（私有或未公开参考）。

## 3. 与首版有关的性能结果

下表为并发 1、热身后的 p95，单位毫秒；每格 300 个正式样本。PostgreSQL 一侧包含查询及正文读取；Neo4j 一侧包含图查询及 PostgreSQL 正文回读。这是实验进程内的数据库调用耗时，**不包含浏览器、HTTP API、登录、完整生产权限校验和页面渲染**。

| 业务查询 | PostgreSQL | Neo4j + PostgreSQL |
|---|---:|---:|
| A1：猜想的有效支持与反对 | 0.39 | 1.22 |
| A2：按证据来源运行分组 | 0.82 | 0.85 |
| B1：知识块的直接引用位置 | 0.31 | 1.23 |
| B2：知识修订的传递影响与解释路径 | 1.76 | 5.90 |
| B3：受影响路线、批注及原有验收事实 | 1.22 | 9.45 |
| 14 类查询中最大的 p95 | 2.45 | 9.45 |

并发 4 时，14 类查询中最大的 p95 分别为 9.64 ms 和 69.92 ms；这是各查询 p95 的最大值，不是将所有查询混合后的总 p95。本轮正式样本未发生结果截断。

预先提出的目标为局部查询 250 ms、影响分析 1 s。实验数据库部分均有明显余量；完整产品仍需测量包含权限与 API 的请求耗时，不能直接宣布产品已达到目标。

中样导入单次观测为 PostgreSQL 1.16 s、Neo4j 4.20 s。此操作包含清空实验数据、导入与索引相关工作，没有重复测量，不能作为稳定导入能力的排名。

性能外推边界：

- 正文较短且为合成文本；没有导入整个课件库。
- 随机背景依赖主要为浅层；没有完成大样或稠密深图压力测试。
- 路径深度有界，但结果上限 200 在完整读取后才应用，不是服务端计算预算。
- 并发测试为查询并发，未验证并发写入和结构环插入的事务隔离。
- 测量未清空操作系统缓存；不称为冷缓存。既有业务负载没有冻结。
- 容器资源采样只能说明被采样时的观测，不能直接给出生产容量或完整峰值。

## 4. 查询语义与维护审阅

两个实现都显式处理关系类型、状态、审查条件、可见空间和快照。PostgreSQL 采用关联表和递归 CTE；Neo4j 采用独立 RelationRevision 节点和量化路径，两者都要维护这些业务规则。此实验没有足够证据证明一种查询语言在长期维护上占优。

已确认的范围差异和后续要求：

| 实验实现 | 首版实现还需完成什么 |
|---|---|
| B1 返回每个 occurrence 对应的边 | API 分别返回去重后的消费者与具体出现位置 |
| B3 将学习实例、批注、验收事实一起返回 | 明确区分需要复查的候选与应保留的历史事实，不能让验收记录自动变成待更新内容 |
| A4 直接读取 `basis_refs` | 固定历史依据；同时对已隐藏/撤权的端点执行当前可见性策略，不泄露对象标识、路径或计数 |
| B6–B8 基础查询读取固定位置与迁移载荷 | 实现真实插入、发布、拆分、迁移确认和回滚事务；保留完整 occurrence 路径 |
| 维护脚本可直接修改实验修订行 | 产品中创建不可变的新修订并切换当前视图；旧内容和学习事实保留 |
| `bodies(ids)` 直接按 ID 回读正文 | 在权威库中重新校验当前权限和请求版本，正文内容也纳入正确性断言 |
| 结构环检查为单写者先查后写 | 对并发请求采用可证明的事务串行化或锁定策略，并验证竞争场景 |
| 最小 outbox 为同步调用与顺序重放 | 实现持久 Worker、失败重试、批次就绪和监控；并发消费及故障恢复另测 |

补充暴露检查已执行：可见结论的 `basis_refs` 指向后来隐藏的证据，以及可见个人事实的 `target` 指向后来隐藏的知识块。两个数据库都返回了隐藏 ID，正文 helper 也能读出隐藏正文。共 4 项 `production_security_pass=false`，保留在 `results/security-boundary.json`；没有修改历史测量或假称修复。这是原型授权与输出实现缺陷，不是选择某种数据库就能自动解决的问题。

首版需在权威查询层校验当前授权和请求版本，明确历史引用在撤权后的展示规则，并把载荷引用、正文、路径和计数一并纳入回归。已授权历史内容如何保留与展示，必须由产品规则明确，不能由“旧快照存在”推断永久有读取权限。

## 5. 同步、位置与恢复演练

- 最小 outbox 记录显示：图服务停止时 PostgreSQL 仍能写入；重复、乱序和图提交后未确认的重试得到预期投影；批次有缺口时未标记就绪；旧修订可查。
- 100 次同步单写者投影 p95 为 6.33 ms；104 个事件重放耗时 0.345 s。这是脚本同步调用的结果，不是异步 Worker 的服务承诺。没有真正杀死长期 Worker，也未验证重建期间持续写入。
- 完整中样从 PostgreSQL 的实体表、关系表重建 Neo4j 耗时 6.522 s，重建后 280 项查询全部与参考一致。来源任务已检查记录中的实际值与预期值。
- 追加位置演练实际插入了新修订和 occurrence、确认迁移、切回旧视图，并保留新旧学习事实。但 `life-K@3` / `life-K@4` 共用同一个稳定块身份，尚未证明“一个块拆成两个独立稳定块”的完整语义；多步操作也不是生产原子发布事务。
- 实验结束后两个实验数据库已停止、卷保留；最终主机记录显示既有业务服务仍在运行。未执行大样、独立备份恢复或完整编辑器验证。

## 6. 设计如何落地

首版继续采用模块化单体 API + Worker + PostgreSQL + 原件存储。关系数据与正文共用权威身份和事务，前端可以立即提供反向链接、支持/反对列表、关系图和修订影响面板。图形展示不要求后端必须使用图数据库。

查询接口按用户问题拆分，例如 `evidenceFor(revision, scope)`、`consumersOf(revision, view)`、`impactOf(revision, rules, limits)`。返回修订 ID、关系修订、出现位置、解释路径、所用视图及是否截断；不向前端暴露某种数据库查询语言。

实现下一步以一个端到端切片为界：打开固定文档 → 在两个块之间插入笔记/图片 → 给猜想连接证据和反例 → 修订一个知识块 → 列出受影响材料 → 只升级选中的文档 → 验证旧快照与旧笔记。数据库设计优先落实不可变修订、Occurrence/Placement、RelationRevision 和事务边界。

满足下列任一业务触发条件，再重开 Neo4j 评估：

- 真实高频多层查询在索引、查询计划和明确预算优化后仍超过既定目标。
- 新增路径模式或图算法成为核心交互，且多次实际需求变更表明图实现明显简化维护。
- 真实关系密度或深度显著偏离本次夹具，并且业务确实需要完整处理这些查询。

届时使用脱敏真实分布重测，并将“权威权限复核、版本就绪、断点重建、重复与乱序事件、并发写入”纳入采纳门槛。Neo4j 仍只作为可重建读模型，PostgreSQL 继续持有权威记录。
